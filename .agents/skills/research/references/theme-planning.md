# 主题级调研计划维护

主题计划回答“这个主题要解决哪些问题、已有成果和剩余工作是什么”。research 独立维护对象调研计划，research-analysis 独立维护分析洞察计划；两者共用本规则、模板及 research-report 回写能力。计划与单次任务的 outline／fields 分别管理。

保存位置、目录模板和收口规则统一见 [交付规范](delivery-policy.md#主题计划的保存与收口)；创建正文使用 [主题计划模板](theme-plan-template.md)。不新增一套任务 JSON，也不把计划表当作证据。

## 定位与创建

1. 从请求判断是否是持续主题、分阶段／多对象研究或明确的主题计划维护。先查项目内已有主题计划，以主题标识、名称、别名和研究目标去重；多个实质匹配时明确目标。用户只查单个事实时直接回答，不建主题计划。孤立的一次调研不因分类为 general 就自动生成“通用主题计划”。
2. 存在明确归属的计划时复用；需要新计划时，research 使用 `research-reports/<主题名>/plan.md`，research-analysis 使用 `analysis-reports/<主题名>.plan.md`，主题目录为英文 slug。theme_id 与 classification.theme 对齐，工作编号属于“报告根目录＋主题”；同名主题的两个入口计划可相互引用，不混合编号或复制同一工作范围。旧计划仍原地维护，不复制出第二份当前计划。
3. 先按 [已有成果核对](routing.md#已有成果核对与复用) 区分可采用成果与实际缺口，再写清目标、纳入／排除范围、问题、任务、评估、优先级、依赖和交付。research 计划使用 paper／open-source／product／benchmark，survey 归 paper；analysis 计划仅用 analysis，基础报告登记为来源或跨入口依赖。资料未核实则说明暂定，不为了填表编造指标，不因对象研究有计划就强求另写分析报告。
4. 只要求计划时保存计划并汇报路径、建议的下一步后结束，不创建空报告、空引用目录或无用的执行任务。未知对象和日期明确待定；不编造负责人、截止时间、资料读取或研究完成状态。

### 创建步骤与最低要求

创建按“定位去重 → 明确边界与工作类型 → 核对已有成果 → 分解实际缺口和任务 → 按类型初评 → 排阶段 → 核对并保存”执行。先确定稳定 theme_id 与唯一当前计划位置，按模板填写实际日期、revision=1、status=draft；沿用已有计划时保留原 ID、created_at 和历史，不重置修订号。用户已明确目标、对象与执行要求，且开始本次任务时可转 active，无须再次确认普通计划内容。

新计划至少有：目标与范围、可回答的核心问题、关联任务、实际类型、优先级及依据、依赖、预期成果、验收条件和下一步。计划内前置 ID 必须存在，不依赖自身或形成循环；跨入口依赖用对方计划／报告的项目路径和工作 ID 一起标识，不能把另一计划中的同号 T001 当作本计划任务。阶段顺序满足依赖，既有成果、本轮工作与待核实历史分别记录。

资料不足时先保存有用的 draft：未知对象或背景明确待定，权威性／影响力和机构／资金关系按类型记待核实，排序说明暂定依据，计划日期可待定。保存 draft 不自动执行待办，也不声称已完成候选核查。主题目标尚未形成实质差异时复用当前计划；目标确实独立时另建主题并互记关系，不以更改标题重复建计划。

保存前核对模板占位符已替换或裁剪、问题／任务／阶段 ID 一致、依赖可执行、实际链接存在、预期路径未冒充成果，并且没有机器绝对路径或 .tmp 链接。仅交付主题计划时无需虚构报告或运行报告 verify；按本规范人工核对即可。

## 问题、任务与成果关联

- 用稳定的问题 ID（如 Q001）和任务 ID（如 T001），修改名称或排序时保留 ID；取消的任务保留原因，不回收编号。每个任务对应至少一个核心问题，一个报告可覆盖多个任务；不要为了对齐计划表重复创建同一对象的报告。
- 任务列出类型、目标、问题 ID、优先级、前置任务、状态、预期报告位置和实际成果。未生成的报告位置写成行内代码及“预期”，不创建虚假链接；报告存在后才填写从计划文件出发的相对 Markdown 链接。
- 单次执行仍按 task-management 创建 light／full 任务，将相应目标落实到 outline.goal、items 和 fields。主题表记录实际 run_id（纯文本）及持久报告路径，不链接 .tmp 内文件，不把临时 run_id 当作主题任务 ID。
- 已关联主题计划的执行任务按下节保存本次范围快照，notes.md 可另记续查提示。计划中跨类型任务共用一个主题标识，报告继续存放在各自 type 目录；单次 --topic 是调研标题，--theme 是分类标签，两者不等同于主题计划的完整内容。
- 计划中的待办不自动授权执行。只推进用户本次要求的任务或阶段；新增任务、依赖或计划日期不自动触发后续调研、外部操作、Git 提交或推送。

## 依赖的满足、失效与复核

前置依赖按“下游任务需要前置任务的哪份成果，满足什么条件才能使用”定义，不只列任务 ID。主题计划用稳定依赖 ID（如 D001）记录下游／前置任务、hard／soft、所需成果或具体主张、接受条件、当前判定、影响范围、来源及核对日期。任务表的前置列只做摘要，依赖表维护条件与判定，不能两处定义冲突。执行前置关系不得自指或成环；普通互相引用不当作执行前置。

- hard：缺少所需成果就不能完成该依赖覆盖的工作。条件未满足时暂停这部分；已获授权且不依赖它的工作可以继续，但不以猜测填补依赖结论或声称全部完成。
- soft：补充材料或参考视角，缺少时可按原目标继续，但要记录为何不影响核心验收、缺失限制及替代来源；如果实际已不可或缺，改为 hard 并记录原因，不能维持 soft 来绕过缺口。
- 旧计划只有前置任务 ID 时，默认 hard，按“前置当前验收完成且所需成果仍有效”检查；需要提前接受部分成果时，先补充明确的片段接受条件。不得为了让下游通过而事后降低条件或把 hard 改为 soft。

### 满足判据

依赖只有在指定成果实际存在、相关内容已核对、版本／时间／场景符合接受条件、关键来源可追溯且没有影响所需结论的未解决问题时，才标“满足”。记录实际采用的报告、章节／主张、版本／日期及所回答的问题；受管前置报告还应完成最终 verify。verify 成功、前置状态 done、文件存在各自都不足以单独证明该依赖满足。

| 前置情况 | 依赖判定与下游处理 |
| --- | --- |
| planned／in_progress，所需成果尚未产生 | 标未满足；hard 覆盖的工作等待，soft 按已说明的限制继续 |
| partial／blocked，但已有独立有效的所需片段 | 仅当该片段满足事先明确的接受条件、限制不影响下游问题时可标满足；保留前置原状态与其他缺口，不把整个前置改为 done |
| done，但所需报告缺失、版本不符或具体结论仍未核对 | 不因 done 放行；尚未核对记待核对，已知不合条件记未满足，曾满足而成果不再有效记失效 |
| deferred／cancelled 或主题暂停 | 不自动满足，也不自动否定已交付成果；已有成果仍符合条件则可复用，否则 hard 继续受阻，替换依赖或调整范围须留原因 |
| 同一前置有多轮成果或替代来源 | 指定实际接受的版本与片段；新版本未复核时不默认为可替代旧版，采用替代前置须更新 ID 关系和接受依据 |

依赖判定仅使用“待核对／满足／未满足／失效”，与任务 planned／partial／blocked／done 等状态分开。首次尚无所需成果是未满足，无法确认现有成果是否合条件是待核对；失效表示此前已接受的成果或接受条件发生实质变化。任一 hard 未满足或待核对时，任务不能标 done；已有独立部分结果可为 partial，无法推进时为 blocked。没有满足证据不能留“满足”。

### 失效后的影响复核

前置结论被修正或撤回、实际采用版本／数据／场景变更、所需文件不可用，或下游接受条件发生实质变化时，重开相关依赖判定。仅前置状态、修订号、排期、措辞或无关章节变化，不自动使有效成果及全部下游失效。

1. 先定位实际被下游使用的成果、章节／主张和版本，对照变更内容。保留原接受记录，新增变更、影响判断及日期；不能覆盖成从未接受过。
2. 被影响或尚无法确认的直接下游标明待复核依赖和具体问题，暂停依赖它的结论回写。已知有效性丧失记失效，影响尚不清楚记待核对；无关下游保持原状态并简记依据。
3. 将确认受影响的任务按实际情况回到 planned（尚待复核）、in_progress、partial 或 blocked，不增加混淆任务与依赖的状态；同步对应问题、阶段及总体收口判断。原报告保留为历史版本，不能继续当作当前有效结果。
4. 按源头变化到实际消费者逐层检查。如果直接下游产出未变且仍有效，停止该路径的扩散；若其产出也受影响，再检查实际使用它的后续任务。不只查一层，也不把所有可达任务一律作废。
5. 复核后更新接受版本／片段、条件、判定与依据，再更新任务状态和成果回写；仍不能满足时保留缺口或经当前范围决策替换／取消依赖，不静默删除原关系。

执行中实际采用新的前置成果时，在 notes.md 或证据记录中保存依赖 ID、版本和用到的主张，回写计划时保留持久摘要。开始、恢复、前置成果变更、成稿、交付回写及阶段收口时都核对相关依赖；依赖图、状态及其传播由代理按规范维护，现有 verify 不会自动检查主题计划的依赖或替代语义复核。

## 本次执行范围快照与回写前对照

仅在确实执行已关联主题的任务时，在该 run 的 `<work_dir>/scope/001.md` 保存范围快照；它属于本次临时资料，主题计划不链接该文件。只编辑主题计划不创建快照或受管执行任务。快照由代理读取计划和当前 outline／fields 后填写，现有报告 verify 不会读取它或比较主题计划。

快照至少记录：

- 计划的项目相对路径、theme_id、开始时的 plan revision、实际记录日期和 run_id。
- 本次主题任务 ID、问题 ID，以及它们与单次 items／fields 的映射；light 对应本次整份 brief。
- 当前任务的目标、问题原文、实际对象类型、对象／版本／时间口径、纳入和排除范围，以及与本任务相关的主题共同边界。
- 本次验收条件原文、预期报告位置和明确未覆盖内容；不能只保存修订号、问题 ID 或文件散列。
- 本次依赖 ID、hard／soft 及接受条件原文，开始时已接受的前置成果／版本与使用范围；执行中新取得成果的接受记录另写 notes.md，不重写原快照。

开始执行前核对快照与 outline.goal、items、fields／light 范围一致。恢复执行、生成／更新报告、回填主题状态前重新读取当前计划，对比上述本次范围及验收；计划路径、ID 和 revision 用于定位及审计，不作为问题未变的证明。

| 对照结果 | 处理与回写条件 |
| --- | --- |
| 本次范围和验收未变 | 继续复用有效证据；记录当前核对日期及计划修订号，再按实际报告覆盖回写 |
| 仅其他任务、排序，或与本次判断无关的背景／章节改变 | 不因这些无关变化使本次证据过期，不要求全部重查；保留原快照，并记录为什么变化不影响本次目标 |
| 本次问题、对象／版本／时间、相关共同边界、验收或依赖接受条件有实质变化 | 标出受影响任务／字段，按正常增量流程同步 outline／fields 和补查状态；依赖按上节复核，证据与报告核对后才回写，不把旧范围的 verify 成功当作新目标完成 |
| 任务被取消、拆分、合并，或暂时无法确认对应关系 | 保留旧成果，先确认新任务映射和适用范围；不能直接把旧 done 转给新任务或覆盖当前计划 |

发现差异时先保留旧快照及对照结论。需要继续执行变更后的已授权范围时，完成范围同步后新增 scope/002.md 等连续编号快照，记录它替代哪份执行口径、变化原因及需复核字段；不得重写 001.md 来掩盖差异，也不把新快照当作证据已重新核实。新范围超出本次授权时，记录待补查与影响，按当前授权继续可独立完成的工作。

对照结论可记入当前任务 notes.md；每次正式回写时，在长期计划的执行／回写记录保留 task ID、run_id、起始／当前计划修订、对照结论、实际回答与未覆盖的验收内容、报告版本／日期及链接。没有满足当前验收的部分结果保留 partial 或相应待补查状态，不能仅凭原报告完整或 verify 通过就标 done。纯排期变化本身不改变证据有效性。

清理前保留这些持久摘要和缺口，范围快照仍随本次 .tmp 按原确认规则处理。快照对照不能替代来源时效检查、论证复核或最终报告 verify。

## 权威性、影响力与优先级

为每个调研项建立评估行，通过稳定任务 ID 关联任务表。对象调研分别记录权威性、影响力及依据；analysis 默认评价论证可信度、问题相关性、解释价值与洞察稳健性，不例行填写影响力。记录适用维度的依据、来源、核实日期及其对优先级的影响。等级使用高／中／低／待核实；“低”需要反向或不足的证据及说明，信息缺失本身记待核实，不自动降为低。等级针对当前主题和研究问题，不作跨领域的通用排名。

先确定对象调研或分析洞察及实际类型，读取对应类型标准中权威性、影响力及“计划中的背景字段”，再按 [对象背景与利益关系](object-background.md) 的共同核实方法填写适用事实。计划的背景摘要与评估行都要标明对象及类型；通用背景线索不覆盖类型定义，不要求所有对象填写公司、客户或融资。适用时记录机构与资金背景的具体角色和依据，不只填名称或笼统的“有资本支持”。

analysis 重点评价成果依据、综合与解释价值、样本边界及可选观点归属，来源对象已有背景仍适用时沿用；只有相关机构、资金或利益关系实际影响本轮判断才补查。对象调研则按其实际 type 的评估标准，使用其中定义与等级参考。权威性与影响力的具体含义由类型规范维护；本节只维护共同的证据、排序和更新规则。不能仅填写“高权威／高影响”，必须记录类型口径和证据。影响力高的对象也可能需要批判性核查。

| 对象类型 | 权威性的定义 | 影响力的定义 | 具体依据及高／中／低等级参考 |
| --- | --- | --- | --- |
| paper | 学术可信度：研究主张的论证、方法和实验证据是否可靠 | 对后续研究、方法及技术路线的实际影响 | [论文评估标准](../../research-paper/references/selection-criteria.md) |
| open-source | 工程可信度与参考实现地位：是否能作为相关技术的可靠实现依据 | 下游工程采用、生态依赖及实现扩散 | [开源项目评估标准](../../research-open-source/references/selection-criteria.md) |
| product | 领域专业地位与能力可信度：专业交付及实际能力是否有依据 | 目标市场的实际采用、平台生态与工作方式影响 | [产品评估标准](../../research-product/references/selection-criteria.md) |
| benchmark | 测量有效性与评估可信度：是否可靠衡量目标能力 | 独立评测采用及对研究比较、选型决策的影响 | [评测评估标准](../../research-benchmark/references/selection-criteria.md) |
| analysis | 依据可靠性与分析过程可复核性 | 默认看解释价值、问题相关性与洞察稳健性，已有影响按需回顾 | [分析洞察评估标准](../../research-analysis/references/selection-criteria.md) |

同一对象兼具多种身份时，以本次研究问题选择口径；确需双视角时分别记录，不混成一个等级。跨类型对象分别复用已有成果或补查并评价；analysis 单独评价依据与推导，不对其来源对象统一改类型。报告的目录分类不改变 item.type，论文的引用数也不转换为产品采用或项目工程地位。

机构、团队及投资／资助背景中的相关经验、参考地位、实际资源和合作网络可成为权威性、潜在影响与持续性判断的依据；必须说明与当前对象的具体关系和证据，不能仅凭名称、融资额或品牌定高等级。官方资料对自身能力的一手性不等同于性能或优越性已被独立验证。引用数、stars、媒体曝光不单独定为高影响，也不当作准确性或质量评分。转载、镜像和同源宣传不计为多份独立支持。

来源记录遵循 [证据规范](evidence-policy.md)：给出实际读取的页面／论文／仓库及可核对位置，区分事实、推断与自述；需要取得文章时沿用文章获取流程。计划阶段只做足以支持候选选择的核查，不自动执行整轮深度调研。未读链接只列待查，无法取得数据就注明缺口。变化信息核实时查当前来源；数值附统计平台、截止日期、单位、版本及条件，旧数据保留原日期，不伪装成本次查询。不同领域、发布年限和类型的原始指标不直接相加或强排。

优先级结合核心问题相关性、权威性、影响力、主体／资源背景、成熟度与关键依赖确定；同时考虑本次时效、预期信息增量和核查成本，在理由中写清重要权衡，不默认使用固定加权总分：

- P0：回答核心问题的先决任务、用户明确指定的紧急任务，或阻塞其他研究的关键证据核查。高权威／高影响本身不足以升为 P0；低知名度的先决资料也可优先。
- P1：直接回答核心问题的主要研究项，相关范围内有权威依据、代表性影响或明确的验证价值。说明哪些证据支撑纳入，以及相对其他候选为什么先做。
- P2：补充视角、边界或次要问题，当前对主要决策的贡献较小；不能仅因较新、指标未知或暂时缺少独立资料就归为 P2。

权威性或影响力尚待核实但可能改变核心判断的新工作，可以暂列 P0／P1 并先进行短范围核查，写清理由；暂定优先级不表示对象已被证实。比较时先按问题相关性与依赖筛选，再在可比对象中参考权威性与影响力，保留反例与争议对象的调查价值。任务表维护唯一的当前优先级，评估表解释理由；不另设冲突的分数排名。

新增候选、开始执行、阶段收口，以及出现影响排序的新证据时复核评估；相关的机构归属、融资／资助、关键团队、客户或合作变化也应复核。若等级或优先级改变，同步任务／阶段安排、核实日期及变更原因；沿用既有资料时保留实际核实日期。当前计划保留背景、评估、来源和实际核实日期，相关判断变化时同步记录原因与影响。现有任务 verify 不判断这些等级或排序是否合理，仍需人工核对。

## 状态与更新时机

主题状态使用 draft、active、paused、completed、archived。draft 表示范围仍在形成；active 表示已开始执行；paused 记录暂停原因和恢复条件；completed 表示当前范围已收口，仍可更新；archived 表示这一轮计划已经冻结，恢复时遵循交付规范。状态由实际进展和用户要求决定，不从文件是否存在推断。

任务状态使用 planned、in_progress、partial、blocked、done、deferred、cancelled。实际开始才标 in_progress；有可交付结果但核心问题仍缺失标 partial；不能推进标 blocked；暂缓和取消分别保留原因。done 需要目标已回答、实际报告已复核，受管任务还应通过最终 verify；verify 通过的部分报告仍是 partial。用户改变范围后可记录不再纳入的问题，不能无理由删除核心缺口来凑完成。

下列事件均直接更新当前计划，不另存主题计划副本：

| 事件 | 更新内容 |
| --- | --- |
| 开始或恢复本次研究 | 任务状态、实际 run_id、本次范围及已知依赖 |
| 追加对象／维度，调整问题或优先级 | 对应任务、问题关联、权威性／影响力及来源、依赖、预期成果与变更理由 |
| 阶段报告交付 | 实际相对链接、问题覆盖、完整／部分结果及剩余缺口 |
| 暂缓、受阻或取消 | 原因、影响、恢复条件或替代任务 |
| 清理本次执行目录之前 | 先确认成果链接和重要缺口已写入长期计划，再按原规则确认清理 |
| 主题阶段收口或范围发生重大变化 | 汇总结果，在当前计划更新范围、修订号、成果与缺口 |

每次实质更新递增 revision，更新 updated_at，并在变更记录写明任务／范围及原因；纯错字更正可只更新日期。created_at 保留首次创建日期，日期使用实际本地日历日期；研究来源的访问日期另按证据规范记录。多个任务并行时只更新所属行和相关问题，先读取最新计划，保留他人的条目与变更记录。

### 维护步骤与状态回退

每次维护先读取本入口的当前计划，确认状态与 revision，定位本次问题／任务 ID；再核对实际报告或证据，更新相关任务、评估、阶段、成果及缺口；最后同步日期和变更原因，复查相互引用后保存。写入前若发现别人更新了当前文件，合并对方变化后重做核对，不以旧副本覆盖。

- 只调整主题候选、问题或阶段时，直接维护 Markdown，不要求旧 .tmp、outline 或报告存在。执行中的问题／对象改变时，除更新主题计划外，按增量规范同步本次 outline／fields 及受影响证据；两者不能互相代替。
- 同一任务可跨多次 run，保留相关历史 run_id 和报告日期，不覆盖成“只执行过最近一次”。取消／拆分／合并任务时保留原 ID、原因及替代任务；新增问题继续分配新 ID，不改号掩盖历史。
- 已完成任务遇到版本变化、新问题或反证时，按当前事实回到 planned／in_progress／partial／blocked，注明为什么旧成果不再充分；保留旧报告、原日期及已回答内容。不能因曾经 done 就跳过复查。
- 主题 paused／archived 时不自动展开研究。用户明确要求继续相应任务可按其授权恢复：paused 记恢复原因；archived 直接修订当前计划，更新状态与日期并记录恢复原因。无需因这一正常恢复动作再次询问相同授权。
- 新增任务不会自动改变已完成问题的证据；核心范围扩大则重新检查 completed 是否仍成立，必要时转 active 并保留本轮变化。阶段结束不自动将整个主题标 completed 或 archived。

维护后汇报计划位置、当前修订号、本次修改的任务／问题、成果与缺口，以及建议下一步。前置成果或接受条件改变时按依赖规则同步相关关系和受影响下游，保留原接受记录；hard 缺口未解决或影响复核未完成时不能据旧 done 宣称阶段完成。阶段任务和问题覆盖决定总体状态，不按完成任务数的百分比或文件数量代替验收。

## 流程接入与交接

| 入口／阶段 | 主题计划操作 | 执行任务操作与交接条件 |
| --- | --- | --- |
| research 新建或恢复主题 | 核对对象成果，在 research-reports 中维护对象调研计划 | 仅要计划则保存后结束；执行交给 research-deep。分析请求直接交接独立入口，不先新建 research 计划 |
| research-add-items／add-fields | 区分同类型对象、跨类型对象、分析问题与来源，更新实际缺口和依赖 | 同类型扩充原任务；跨类型复用或建立独立任务；新增分析来源不增加来源对象到 items；只改计划不要求 .tmp |
| research-deep 开始／续查 | 检查本次依赖的实际满足情况，建立／对照范围快照并回填进展 | hard 未满足的部分暂停；独立工作仍可继续，前置变化只复核实际受影响范围 |
| research-analysis 开始／续查 | 记录采用成果、分析主题／问题、样本范围、接受条件及可选观点归属；基础缺口单独登记 | 补查按实际对象类型执行后返回原分析，只复核受影响发现；新增分析主题不重做所有来源调研 |
| research-report 交付 | 对照当前目标、验收及依赖，记录接受的版本／片段、报告及缺口 | 回写前复核 hard 条件；前置修订时通知相关实际下游，不凭旧 verify 或 done 放行 |
| 阶段收口／重大调整／主题归档 | 核对当前范围与真实结果，直接更新当前计划的修订、状态及收口记录 | 不生成计划副本、不移动报告；收口不会触发临时文件删除 |
| 清理单次执行资料 | 先确认重要成果与缺口已脱离 .tmp 写入长期计划 | 再走原 cleanup-plan 与确认流程，长期计划保留 |

主题收口与恢复的保存规则只在 [交付规范](delivery-policy.md#收口与恢复) 维护；均在本入口的当前计划中完成，不另存归档快照。现有工具不会自动执行上述主题交接；使用技能的代理负责同步，并如实说明未完成的更新。

## 收口与核对

阶段收口时逐项核对核心问题与任务：完成的给成果，未完成的给缺口与后续安排；deferred／cancelled 不算完成。completed 要求当前纳入范围的必要任务和问题已完成，范围调整有依据；如果停止研究但仍留缺口，可直接归档并明确“部分完成／取消收口”，不先伪装成 completed。

主题计划维护按 Markdown 编辑与人工核对执行，现有 research_task.py 不会自动创建、同步或归档主题计划。其 list/show、verify、cleanup-plan 只管理单次受管任务及报告，不作为主题计划的全局校验器。归档前核对主题／版本／任务 ID、问题覆盖、逐项评估与优先级依据、成果文件是否存在、相对链接与剩余缺口；报告可在正文记录主题与任务 ID，但不为了回链计划而突破报告检查器的输出目录边界。

计划可做针对性的语言整理，但主题／任务 ID、状态、日期、范围、依赖、链接和数据保持原意。计划已经有待办或模板内容，不等于所有条目已调研。
