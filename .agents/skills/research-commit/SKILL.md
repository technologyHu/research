# Research Commit：独立报告提交入口

独立负责已有调研报告和分析洞察报告的 Git 提交、提交检查与授权范围内的历史整理。直接读取当前报告、交付记录与文件差异；公共规则按需读取 [research-common](../research-common/SKILL.md)，不调用其他顶层入口。

只处理用户已经明确的提交范围，不重新开展调研、分析或生成报告。沿用用户指定的仓库、分支、报告位置与已有提交习惯。

## 授权与交接

- 用户要求“提交报告”“提交这些调研成果”或明确调用本技能执行提交时，可以创建相应的本地 Git commit，无需逐篇重复确认。仅要求生成、更新报告或创建本技能，不构成实际提交授权。
- 用户只要求检查、列出提交方案时，完成分组与校验后汇报，不执行 commit。没有报告变更时不创建空提交，也不把其他工作区修改当作报告提交。
- 本地提交不自动包含 push、发布、创建 PR 或强制推送。沿用会话内已经明确的授权；不为实现“一篇一个 commit”擅自改写已发布历史。
- 提交范围依据 [共用交付规范](../research-common/references/delivery-policy.md)；成稿及校验沿用 [research-report](../research-report/SKILL.md)。本技能检查临时文件和清理状态，按当前有效授权清理本轮已结束任务的精确范围；不擅自删除、不重新执行整轮调研，也不改变报告的真实完成度。

## 确定每篇报告的提交范围

先读取当前分支、工作区状态、已暂存差异与相关历史，建立“报告 → 精确文件／差异片段”的清单。区分用户既有改动、本次报告改动、其他报告与工具维护改动；未跟踪不等于无用，已暂存也不等于获准一并提交。用户要求“只提交已暂存内容”时以索引版本为边界，不暂存新内容，不带入同文件未暂存修改；普通报告提交才按已获准的工作区最终版本准备。

支持 research-reports 和 analysis-reports 中的成果，兼容已有旧位置。一篇报告对应一个独立交付单元：

- 新布局为 `<report-dir>/`：paper、open-source、product、benchmark 的 report-root 为 research-reports，analysis 为 analysis-reports。主文件默认 report.md，自定义名读取 outline.delivery.report；兼容既有位置，不为提交搬迁目录。
- 同一对比报告分析多个对象时仍算一篇。随主报告交付的补充 Markdown、术语表属于同一单元；独立成稿、可单独交付的另一篇报告单独分组，不能只按目录或文件扩展名猜测。
- 随报告提交同名的 `.meta.json`、实际引用的 `references/`、`assets/` 与已登记的必要额外交付。旧格式报告的元数据在正文内。按任务配置和文件差异核对归属，不递归暂存整棵主题目录。
- 报告修改导致的附件更新、废弃附件删除、必要链接修正一并纳入该篇提交。共享附件按实际归属提交一次，多个报告按依赖顺序提交，不为凑分组重复复制资源。
- `.tmp/`、工作源码副本、原始结果 JSON、运行缓存、IDE 配置和未登记实验产物不随报告入库。用户明确要求的额外交付按共用交付规范处理；不能使用 `git add -f` 绕过忽略规则批量加入资料。

关联计划的成果链接、版本、状态和缺口，应先按 [主题计划维护](../research-common/references/theme-planning.md) 回写。单篇独占且已获准的计划变更可随篇提交；多个报告共用的计划修改默认留到各篇报告提交后，再用一笔计划维护提交保存，不在报告提交中临时拆分共享文件。用户明确要求分片归入各篇时，先制定可验证的索引隔离方案；无法保留原暂存／未暂存边界时不执行该分片。不为整理 Git 历史改写计划中的事实、日期和实际完成度。暂存内容模式不顺带新增计划修改。

README、图谱数据、预览及图谱工具代码属于共享维护内容，默认交由仓库现有流程更新，不混入每篇报告的提交；用户要求同步提交时明确作为独立维护范围处理。提交操作本身不触发新图生成、格式转换或截图，遵守项目的图像能力约束。保留用户当前明确要求的占位文件和空目录约定。

## 提交前规范检查与轻量校验

每篇 commit 或 amend 前都执行 [提交前检查](references/pre-commit-checks.md)，先读取当前共用规范，再检查实际候选版本，不能因用户已要求提交就跳过。

1. 建立按篇清单，确定工作区／暂存版本及普通提交／amend 的比较基线；一笔提交只含一份独立报告及其获准附件和关联变更。目录改名按同一稳定 ID 认领旧、新路径，不误拆成两篇。
2. 核对目录、类型、注册主题、命名片段、时间后缀、主文件与稳定 ID；旧报告沿用兼容规则，不为提交自动搬迁或更新时间。报告身份冲突、多个报告混入一笔时先处理，再准备提交。
3. 检查本篇临时资料是否已清理或有明确保留依据，并确认候选中没有临时文件、缓存、IDE 配置或 `.tmp` 链接。清理遵循共用规范的验证与授权；已有授权不重复询问，无授权时先完成其余检查，再集中列出精确待清理范围。保留其他任务和未提交新版本的工作资料。
4. 从候选 tree 的隔离快照进行本地文件与链接检查，并对候选差异执行 Git 的轻量检查；不能用工作区的附件补足候选缺失。默认不联网、不重跑实验或生成图片，不把结构通过写成研究完整或论证已复核。
5. 需要任务一致性检查时才追加真实任务的 verify：例如本轮证据、版本、范围或状态发生变化，或清理所需的有效回执缺失／失效。已有回执必须核对当前文件，不能仅凭 `verification_receipt_present` 放行；候选与工作区不同也不能借用工作区回执。已清理的既有任务不伪造 outline 或重新调研，按保存记录完成静态检查并说明限制。
6. 汇总每篇的检查结论、清理／保留状态与实际缺口；必检项有阻塞时不执行该篇提交。`partial` 可如实提交，其他独立且已通过的报告可以继续处理。候选、HEAD 或选定版本变化后重查受影响项。

## 每篇报告独立提交

先把同篇本轮修改整理完成，再执行一次提交，不按章节、来源文件或每次小改拆分 commit。多篇报告逐篇完成本节；有引用依赖时先提交前置报告。纯计划维护请求仍可单独提交计划，不要求先创建报告。

- 对显式文件清单使用 `git --literal-pathspecs`，它适用于 add、diff、ls-files、commit 及 amend 等路径操作；仅有 `--` 和 shell 引号不能阻止 Git 将 `[ab].md` 当成路径表达式。程序读取路径使用 `-z` 并按 NUL 分隔，不按空格或显示出来的引号拆分文件名。不使用 `git add .`、`git add -A` 或无范围的 `git commit -a`。
- 普通工作区模式：对完整归属于本篇的文件精确 `git --literal-pathspecs add -- <files>`。索引只有本篇内容时可正常提交；另有无关暂存文件时，可用 `git --literal-pathspecs commit --only -m '<message>' -- <files>` 隔离。先检查即将提交的候选树，不能只查看文件清单。路径清单包含本篇获准的新增、修改和删除文件。
- 暂存内容模式：禁止使用 `git add`、`commit --only`、`commit -a`；索引完全属于本篇时直接提交。另有无关暂存项时，按 [索引版本隔离](references/git-workflow.md#索引版本隔离) 构造只包含该篇暂存版本的临时索引，验证后用该索引提交，保留原索引与工作区。不能可靠隔离时暂停，不退回提交工作区版本。
- `--only` 会取指定文件的当前工作区版本。一个文件混有其他报告或用户未授权改动时不能直接使用；同篇文件已有暂存和未暂存差异也须先明确选择版本。不清空索引、不覆盖用户差异、不自动 stash 整个工作区。
- 执行前确认 HEAD、原索引及选定文件未被并发修改；范围变化先重查，不照旧清单提交。每篇记录起始 HEAD、候选 tree、精确范围及成功后的提交号，批量执行中每完成一篇立即核对并更新记录；失败按 [中断与恢复](references/git-workflow.md#中断与恢复) 判断，不直接重跑 commit。
- 标题用中文说明对象与变化，例如 `新增调研：Agent Memory 机制分析`、`修订调研：Agent Memory，补充评测与限制`。正文按需记录范围、资料版本／日期、真实校验与缺口，不堆砌工具日志，不把日期代替内容摘要。

## 同篇报告的修订尽量合并

“一篇一个 commit”优先约束本次交付：新报告一笔，同篇的一轮修订一笔；持续研究不要求把所有历史版本永久压成一笔。

| 情况 | 处理方式 |
| --- | --- |
| 本轮修改尚未提交 | 整理完同篇全部修改后一次提交 |
| 本会话刚创建的同篇提交恰为 HEAD，尚未发布且范围纯粹 | 可 amend，将后续修正合回该篇提交 |
| 用户明确指定可修改的同篇本地 HEAD，确认尚未发布且范围纯粹 | 可 amend，重新检查原提交与新增差异的完整范围 |
| 同篇目标提交不是 HEAD，中间夹有其他报告或共同维护提交 | 默认本轮修订新建一笔；用户明确要求整理本地历史时才考虑定向 rebase／squash |
| 已推送、被其他分支采用、归属不明、签名需保留，或无法确认尚未发布 | 保留已有提交，本轮修订集中成一笔新的更新提交 |

amend 前读取 HEAD 的作者、完整文件清单、差异和会话来源；确认只涉及该篇及获准的附属变更。合并提交、混有其他报告／工具改动的提交不能因碰巧包含报告就自动 amend。检查相关远端跟踪引用及本地分支包含关系，结合会话内的创建／推送记录判断；过旧的远端引用不能证明“未发布”，不确定时选择新建修订提交。

使用 amend 时同样隔离其他暂存项；普通工作区模式的独立完整文件可用 `git --literal-pathspecs commit --amend --only ... -- <files>`，保持原提交的其他获准内容。暂存内容模式改用已验证的索引执行不带路径的 `git commit --amend`。候选树相对 HEAD 无变化时不为刷新提交时间而 amend；检查 amend 最终范围时与原 HEAD 的父提交比较。若最终范围改变，重写标题／说明使其描述最终结果；只修正同篇小错误时可保留合适的原说明。先记录旧 HEAD 及其父提交，完成后核对新提交。

只有用户明确要求改写本地历史时才执行定向 rebase／squash：先列出基线、目标提交与将被重写的后续提交，确认未发布、无合并歧义及并发变动，建立可恢复的备份引用，并保持无关提交内容及顺序。索引／工作区不能安全隔离时不启动；不自动 stash，也不顺带折叠其他报告或他人的提交。冲突后先核对实际差异，不能可靠继续时停止并报告状态，不用 reset --hard 或强制推送收尾。普通“提交报告”不包含这项授权。

## 完成与汇报

提交后逐笔检查 `git show --stat` 和实际差异，确认报告、附件与获准的关联变更归属正确；检查工作区和索引，保留原先无关的暂存／未暂存内容。仅有获准内容无变化时说明“无可提交变更”，不创建空 commit。

本技能 Git 操作的行为回归可运行 `python -B <skill-dir>/scripts/test_git_workflow.py`。测试仅在系统临时目录创建隔离仓库，不提交当前仓库，不生成图片；它验证命令流程与文件检查，不代替实际任务中的授权、报告归属或事实判断。

向用户列出“报告 → 提交号 → 新增／修订／amend”、实际校验及仍保留的改动。未能合并历史时用一句话说明原因；失败、被工具策略拦截或钩子拒绝时如实报告，不跳过钩子、不改用户 Git 配置、不换工具规避同一拒绝。区分“已本地提交”与“已推送”，未推送不提供已发布的表述。
