# 源码理解接入调研流程

当本轮研究问题需要核对实现时，由 research-deep 调用 code-understanding 取得源码证据，再回到当前调研任务。

- 调用方管理问题、对象类型、任务、完成度及交付。
- code-understanding 统一负责必要的仓库选择、目标／版本复核、后端选择和源码阅读，返回按原问题映射的证据与缺口。
- research-deep 统一写回原 light/full 记录；research-report 使用这些证据成稿。类型技能仅提供分析维度，后端仅提供分析能力，不另起计划、结果格式或正式报告。

## 何时使用

- 开源项目的架构、关键流程、算法／数据结构、扩展点和实现约束，需要阅读源码时接入。
- 论文的公开实现、benchmark 的评测脚本、产品的公开 SDK 或分析洞察中需复核的代表实现，也可按当前字段调用；沿用原 item/type，不为每个来源仓库创建新对象或报告。
- 只需论文正文、产品文档或协议就能回答的问题，按原路径取得证据。闭源部分保持资料边界，不能从 SDK 推断服务端实现已被核实。
- 用户只要计划时，仅记录需要核查的实现、版本和问题，停在规划阶段；不因此初始化后端、建索引或开始源码分析。

## 确定源码仓库

仓库发现、身份与版本门槛、问题覆盖及选择状态统一遵循 code-understanding 的 [仓库选择与记录](../../code-understanding/references/repository-record.md)，在该入口执行一次。调用方传递指定代码和已核实来源，无须提前选完仓库；已有选择仍适用时复用。

仅需要完整选择记录的任务才保存 `scratch/code/<item_id>/repository-selection.json`；普通指定代码阅读直接绑定目标，在已有笔记／证据中记录实际版本即可。源码选择的 selected／partial 不等于研究完成，源码结果的未知部分仍按原研究字段保留 unknown 和缺口；没有源码实现时继续独立资料研究，不新增空对象或虚构源码章节。

## 交接给代码理解入口

传递已有上下文；尚未确定的目标或选择依据可留待入口补齐，不先启动另一轮顶层工作流：

| 上下文 | 内容 |
|---|---|
| 调研归属 | 当前 work_dir、workflow、item_id、问题／field_id，以及关联主题任务和验收要求 |
| 源码目标 | 用户指定或已核实的一个或多个仓库 URL、本地真实路径、要求版本／提交；本地源码可以在任意其他目录或磁盘 |
| 分析范围 | 本次要回答的行为、模块、调用链或文档对应关系；已有来源、已接受证据及待查缺口 |
| 版本条件 | 计划版本、实际 commit／tag、worktree、未提交变更，以及先前分析使用的源码上下文 |
| 选择依据 | 已有选择记录或来源及其缺口；有完整记录时包含身份／版本映射、问题角色分配、源码可读性与运行状态 |
| 回写位置 | 当前任务的 `code/<item_id>/<repo_id>/` 保存确有需要的源码副本；`scratch/code/<item_id>/` 保存对象级选择记录，`repos/<repo_id>/` 保存各仓库的预检、摘记和工具结果 |

技能安装位置、源码位置和调研工作目录是三个独立基准。工具与运行依赖从技能位置解析，源码和 Git 上下文绑定目标 checkout，调研证据回写当前 work_dir。research_task.py／validate_results.py 的命令仍以 outline 对应的调研 workspace 为基准；后端切换 cwd 不得改变 work_dir、output_dir 等调研路径的解释。不要把 external repo 自动当作当前任务的项目根，也不要因为调研材料保存在本仓库就分析本仓库自身。

入口对每个实际目标执行 preflight，再按问题使用后端或直接阅读源码；记录后端、版本、分析范围与限制。`repo_id` 是本任务内唯一的目录 slug，同一仓库的不同版本／checkout 也分开，不直接拼接不受控的仓库名称。示例（相对 work_dir，按需创建）：

```text
scratch/code/<item_id>/
├── repository-selection.json       # 需要完整选择记录时才保存
└── repos/<repo_id>/
    ├── context.json                # 此 checkout 的 preflight
    ├── gitnexus/                   # 此 checkout 的 GitNexus storage
    └── graphify-out/               # 此 checkout 的 Graphify 输出
```

恢复已有单仓库任务可沿用旧 `context.json` 和工具位置，不强制迁移；新增仓库另分目录，不能覆盖原上下文。选择与预检记录均为工作资料，不能替代逐条证据。

## 源码与工具输出的位置

已有的外部源码和有效索引可以原地读取；这些既有资料不归本次任务所有。需要新的源码获取或临时分析时，按 [交付规范](delivery-policy.md#中间资料) 放在本次任务内，避免将工具生成文件散落到最终报告目录或修改用户既有源码树。

- GitNexus 用 `GITNEXUS_STORAGE_PATH` 指向对应 `repos/<repo_id>/gitnexus/` 的绝对路径；需要隔离注册信息时使用任务专用 `GITNEXUS_HOME`。建立静态索引时使用相应 skip 选项，避免自动写入目标项目的 AGENTS/CLAUDE 文件或安装技能。注册项目按真实路径和明确标识匹配，同名仓库／不同 checkout 不能只凭显示名称选择。
- Graphify 在进程启动前把 `GRAPHIFY_OUT` 设为对应 `repos/<repo_id>/graphify-out/` 的绝对路径；后续查询沿用同一值。上游编号流程仍有字面量输出路径时，改为本次明确的任务路径，或在任务专用源码副本执行，不能假定环境变量会覆盖所有手工命令。已有图谱的快速查询也须先核对目标版本和覆盖。
- Understand Anything 默认在目标项目创建 `.ua/`。已有图谱先核对；需要新建且用户未要求向既有源码树写入时，使用本次任务内的源码副本，绑定副本与原始 checkout 的版本和变更关系。保持指定 worktree，避免自动重定向到另一个 checkout。

不能把只包含已提交内容的 clone 当作包含用户未提交修改的工作树副本。若分析指定发布版，核对 tag 到 commit 的映射；若分析本地修改，则保留基准 commit、变更摘要和实际读取位置，不能用发布版链接冒充修改后实现的直接证据。

静态索引／源码阅读与运行被调研项目的安装、测试、服务和 benchmark 是不同操作，运行行为按 [执行规范](execution-policy.md) 与用户本轮授权判断。后端缺失或准备失败时，继续能够完成的源码阅读并保留能力／证据缺口。

## 返回证据并统一写回

code-understanding 按原问题／field_id 返回具体结论、原始源码位置、版本／配置条件、推断与运行状态及缺口；不引入新的结果 schema。research-deep 按 [证据规范](evidence-policy.md) 和 [配置约定](research-config.md) 写回一次：

- **light**：将具体结论、实际采用版本、源码文件／符号／行号、依据与缺口写回当前 `notes.md`，按任务管理填写原有 `outline.assessment`。不另外创建一份正式导览报告来代替研究笔记。
- **full**：将结论映射回本次已有的 field_id，写入 `results/<item_id>.json`。沿用标准 `sources`、`evidence`、`status`、`reason` 和 `input_fingerprint`；不能凭后端图谱或总结自动设置 confirmed。
- `sources` 登记实际阅读的原始源码／文档。公开源码优先使用固定 commit 的永久链接，`evidence.locator` 记录文件、符号和行号，`supports` 写明它支持的具体主张，`conditions` 写清版本／配置及是否执行。纯本地／内部源码按已有权限记录真实来源及可复核限制，不伪造公网链接。
- 模型的模块划分、业务映射或推断边，回查源码后再决定 confirmed／inferred；有证据但仍需推导时填写 reason。静态调用链不等于运行轨迹，存在测试文件不等于本次测试已通过。

下面仅演示现有字段的用法，示例 URL、版本、日期和行号都须替换为实际核对值；对应 source_id 需先登记：

```json
{
  "source_id": "source-router",
  "locator": "src/router.ts:dispatchRequest，L42-L67，commit <实际提交>",
  "supports": "请求先经过注册的中间件，再进入匹配的处理函数。",
  "conditions": "固定提交的默认配置；本次仅阅读源码，未执行服务。"
}
```

本次预检和工具产物是导航与分析记录，原始实现才是关键源码主张的来源；不要把同一源码的三份图谱总结算成三份独立证据。暂时无法核实的核心实现问题按原规则保留 unknown 和缺口。

## 续查、成稿与清理

恢复任务时逐仓库对照先前源码上下文、当前 checkout、工作树变化和索引覆盖。研究字段的 `input_fingerprint` 绑定研究问题／范围，不自动检测源码内容变化；现有结果检查器也不会读取 context.json 来证明源码仍一致。

需要选仓记录时，按其复用规则复核并运行选择检查；validate_results.py 不自动验证它，也不要求普通指定代码任务补建记录。实际源码状态仍需单独复核。

源码或相关材料改变时定位实际受影响的字段／主张，将对应进度标为 stale，复查后再按原流程更新输入指纹与 done 状态。不能只刷新图谱或覆盖 context.json 就沿用旧结论；与本次字段无关的源码变化不要求重做全部研究。light 问题或版本改变时沿用整份复查／promote 规则。

证据写回后继续原 research-deep 的 validate 和完成度判断。将需保留的身份依据、研究与代码版本关系、问题覆盖及运行限制写入已有笔记／证据与报告；成稿引用原始固定源码与相应条件，不链接会被清理的选仓 JSON、索引、`.tmp` 或本地临时副本。报告和工具图谱的版本不一致时，返回当前任务补查相关字段，不由后端另开研究计划。

工具生成的 Markdown、HTML、JSON、模型缓存和源码副本按原交付规范处理；用户明确要求的导览／图谱文件才登记为额外交付。清理仍由原受管任务的精确范围确认流程管理，不删除任务外既有源码、原有索引、共享工具运行环境或用户模型缓存。
