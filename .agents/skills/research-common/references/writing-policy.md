# 中文报告写作规范

先回答研究目标，再展开证据与机制。模板是分析框架，不是要求每个项目都填满所有章节。简要研究合并章节，详细研究围绕关键机制展开，避免只贴目录、堆术语或逐段翻译文档。

## 内容组织

- 用任务管理脚本生成本次状态说明并放在标题下，保留可见的完成度、版本和核心缺口。开头写清主题、资料日期、研究范围与主要结论。部分报告要说明核心缺口对结论的影响，不能将“结构检查通过”表述为“调研已全部完成”。
- 结合所选对象类型的模板组织章节。横向比较先统一问题和口径，再给比较表与逐项分析；不适用与未知分别标明。
- 关键结论、定量数据与实现细节就近引用原始来源；适当引用固定版本的路径与行号。
- 术语首次出现解释其含义与作用，复杂机制用具体过程或例子串联。
- 局限、反例和未执行验证直接写明。所有适用 unknown 都保留问题和理由，核心与非核心缺口分别说明；完成度为完整不代表没有非核心缺口。沿用证据保留原访问日期，不表述为本次重新核实。
- 来源有冲突时，依据 [证据规范](evidence-policy.md#来源冲突) 交代各方说法、适用条件和取舍理由；未解决冲突保留为缺口。局部更新依照 [更新流程](report-updates.md)，将完成度限定为本次复核范围，保留未复核章节的原记录。

## 报告开头

标题下只放一段简短说明，写调研状态、所用版本、调研人和北京时间。完成局部复查时写「局部复查完成」。首次交付写调研时间，修订后写最近修订时间。写明仍待确认的具体问题，没有就省略。修订章节、历史记录和证据细节保存在同目录的 `.meta.json`，来源在正文或来源章节引用。

用 `report-note` 预览说明。报告写好后用 `sync-report-note` 同步开头和元数据，正文只放读者需要看的说明。旧报告再次修订时，工具会转换其原有说明。命令见 [任务管理](task-management.md)。

## 图表与代码

先按 [draw-diagram 的图像能力条件](../../draw-diagram/SKILL.md#图像能力条件) 判断当前模型能否实际查看并理解图片。无此能力或无法确认时，只采用用户提供或来源明确的现有图片，可下载、复制和引用原图；不生成、重绘、修改或转格式出图，也不通过代码绘图、Mermaid 渲染、截图或定量绘图库绕过限制。依据原文图注、上下文与版本核对适用性，不推断看不到的图内细节，不声称已完成视觉复核；没有合适图片时用文字或表格，必需的新图无法交付时披露缺口。

报告应按内容需要做到图文并茂。先说明候选图能帮读者理解什么，例如跨组件调用、身份与数据边界、状态变化或有依据的结果差异。没有新增解释价值时保留文字或表格，不设最低图数，不把段落改成方框、添加装饰图或反复展示同一信息来凑图。

先检查用户资料、已获取文章、官方文档和已有报告中是否有相关、清晰且版本适用的素材。有助于了解对象或理解机制的架构图、流程图、概念图、产品界面、软件前端截图、结果图和演示 GIF 均可直接插入相应章节，不限于必须保留原貌的视觉证据；无需先重绘成 Mermaid 或统一风格。没有合适的已有素材，或需要解释新的关系时，再按表达效果、目标阅读器和制作成本选型。新绘默认优先代码绘图，不默认调用图片生成服务：

| 表达需要 | 优先方式 | 何时改用其他方式 |
| --- | --- | --- |
| 已有图能帮助了解对象或理解本节内容 | 直接复用来源明确、可合法使用且清晰适用的原图 | 原图过时、过密、难读、获取受限或无法表达本次重点时，再选其他方式 |
| 产品或软件前端的入口、布局、配置和结果 | 相关界面截图，就近标明用户要看哪里 | 单张图无法解释操作先后或状态变化时，选用有新增解释价值的演示 GIF |
| 操作步骤、交互反馈或任务状态的连续变化 | 来源明确、实际核对过的原始演示 GIF | 阅读器不支持播放、体积过大或内容不可核实时，使用合适的已有静态图及原始演示链接 |
| 流程、时序、状态、模块关系、概念或简单架构 | 目标 Markdown 阅读器支持的 Mermaid 等内联代码图 | 关系过密、版式难读、阅读器不支持或用户要求静态图片时，改用代码生成的 SVG／PNG |
| 有数据依据的比较、趋势或分布 | 定量绘图库或适合该数据的可复现代码图 | 按阅读器支持选择嵌入格式，保留单位、口径和来源；不为出图编造数值 |
| 产品界面、原始实验图、来源材料中的关键视觉证据 | 来源明确、与正文结论直接相关的原图 | 不用自绘替代需要核对原貌的证据，不为省成本重绘成貌似原图 |
| 复杂架构、精确排版、领域图标或需要独立分享的技术图 | 通过 [draw-diagram](../../draw-diagram/SKILL.md) 选择合适的代码绘图后端 | 内联图不能清楚表达时直接制作静态图，不必先机械尝试所有便宜方案 |
| 需要插画、场景、质感等视觉表达，或代码布局不能有效表达的图 | 必要时采用图片生成／编辑工具 | 图片生成仍是可选能力；按实际需要使用，不把成本偏好解释为禁止生成图片 |

架构图同样按复杂度和用途选型，不一律要求图片生成，也不一律限定 Mermaid。优先代码绘图只针对需要新绘的情况，不排斥直接插入合适的已有图。用户明确指定的格式和用途优先；静态交付要求不能用代码块替代。

内联图直接保存在主报告的带语言标记代码块中，就近给出图注、依据和必要的文字解释，不强制再导出 SVG／PNG 或另存源文件。实际阅读器支持已核实时才声称可直接渲染；尚未核实时说明兼容性未验证，若交付必须可见则使用兼容的嵌入图片，不以纯代码显示冒充已交付图。普通代码示例仍需区分概念演示、上游源码和实际验证代码；内联图不自动扩大附加文件交付范围。

中文为默认报告语言，保留必要英文专名、API、命令和公式。参考文章的原文／译文遵循用户要求与 [证据规范](evidence-policy.md)。

### 值得纳入的图与演示类型

在取证阶段就检查官方产品页、文档、论文及附录、仓库 README、发布文章、演示入口和已有成果，按研究问题选择下列素材。类型用于发现有解释价值的内容，不是每篇必须凑齐的配图清单；只记录实际有用的候选及对应问题，不为没有采用的类型逐一写缺失说明。

| 素材类型 | 何时值得插入 | 帮助理解的问题 |
| --- | --- | --- |
| 架构图、组件关系图、部署图 | 需要解释系统组成、模块职责、部署位置或外部依赖 | 系统由什么构成，各部分如何连接，边界在哪里 |
| 流程图、时序图、状态变化图 | 涉及任务执行、调用顺序、多人接续、异步运行或生命周期 | 工作如何推进，哪些状态变化或保留 |
| 产品界面、软件前端和配置界面 | 能展示核心入口、关键操作、配置、进度反馈或协作过程 | 用户如何使用，系统如何反馈，配置在哪里生效 |
| 演示 GIF、动画和视频片段 | 连续操作或状态变化具有解释价值，单张静态图难以说明 | 操作前后发生什么，连续过程如何展开 |
| 关键输出与交付物示例 | 有代表性的报告、图表、文件、PR、任务清单或其他结果 | 最终交付什么，结果如何使用和验收 |
| 实验结果、评测图表和数据分布图 | 数据可追溯，需要解释效果、成本、性能、扩展性、失败模式或适用边界 | 结论有什么数据支持，优势与限制在哪里 |
| 对比图、演进图和概念示意图 | 涉及方案差异、机制变化、版本演进或难以用文字解释的概念 | 关键差异是什么，变化带来什么影响 |

已有素材相关、清晰且版本适用时直接复用，不为统一风格重绘；需要解释新关系时再按上表选型新绘。结果与评测图保留数据来源、指标、单位和条件，不把营销数字或示例输出当作独立评测。关键产物示例保留实际来源，不能自行生成结果来冒充产品交付。

采用的图放在对应正文附近，通过引导正文或图注简短说明展示内容、阅读重点和来源；版本或限制只在影响理解与结论时展开，不逐项复述图中文字，不强套固定图注模板。重复的通用限制集中说明，具体影响判断的限制仍就近保留。重复截图、宣传海报、品牌动效、头像和装饰图通常不采用；文字或表格足够时不必增加图片。

### 已有图复用

- 把图放在它帮助解释的正文旁，说明读图重点，并注明来源、适用版本及必要署名。来源图中的设计或效果仍需按证据强度解释，不把示意图当作实际运行记录，也不把复用称为自绘或新生成。
- 核对图与本次对象、版本及主张是否匹配；模型可看图时检查文字、图例、箭头和显示尺寸。无图像理解能力时沿用上述限制，只依据可核实的图注与上下文使用原图，不推断看不到的细节或宣称视觉复核。
- 保存、来源文章核对与归档沿用 [交付规范](delivery-policy.md#允许交付的内容) 和 [文章获取](article-acquisition.md)。只保留实际嵌入的图片；来自其他报告的图需要复用时，保留其原始来源与适用条件，不把临时路径带入本报告。不为复用而自动裁剪、改字、转格式或重绘；需要修改时按新绘规则处理。
- 已有图同样不设数量要求。与本节无关、只起装饰作用，或与现有图重复表达同一信息时不插入。

### 界面截图与演示素材

- 产品、带前端的开源软件和相关评测工具都可按需采用界面与演示素材。用截图解释用户从哪里进入、需要配置什么、结果在哪里；用 GIF 展示一次有意义的操作及其状态变化。不要求每个对象有界面素材，也不为配图虚构产品界面或启动无关部署。
- 将素材放在对应工作流或能力说明旁，写明演示任务、输入／操作与可见结果，注明来源、版本或发布日期、套餐等影响理解的条件。区分官方发布示例、第三方演示、本次真实操作和自制概念稿；演示中的旧界面或模型名称不自动代表当前产品状态。
- 官方交互演示的静态预览可以作为有用的界面原图，但必须按实际取得的形式说明；没有操作完整流程时，不声称验证了完整演示。进度清单不等于最终交付，指令确认不等于到期执行；按可见状态解释，不从勾选、时间戳或宣传图推算成功率和耗时。
- 具备图像理解能力时，GIF 应实际播放，或结合帧时序核对关键状态、动作顺序与循环；只查看首帧不能声称核验了完整演示。能力不足时沿用已有图复用限制，不宣称动画视觉核验。保留原动画，不默认截成静态图、裁剪、改速或转码，也不为展示已有 GIF 调用动画生成。编辑过、倍速或省略等待的演示不能用于推定真实耗时、成功率或可用性。
- GIF 使用 Markdown 图片语法嵌入，例如 `![任务操作演示](assets/task-demo.gif)`，并检查正文显示尺寸、文字可读性与播放情况。格式识别或文件校验通过不等于动画验收通过；未验证目标阅读器播放时如实说明。视频或交互式演示无法在阅读器内呈现时，就近给原始入口和观看重点；只取得封面不能宣称已观看内容，不默认把整段视频转换成 GIF。
- 获取与归档沿用 [文章获取](article-acquisition.md) 和 [允许交付的内容](delivery-policy.md#允许交付的内容)。只保存实际采用的素材，不把宣传片头、品牌动效、片尾推广或与既有图片重复的演示加入报告。

### 自绘技术图

以下生成与改图流程仅在满足上述图像能力条件时执行；否则止于已有图片的选择、引用和文字核对。

- 组织章节时先确定每张候选图要说明的问题、对应章节、依据版本及能否直接复用已有图；确需新绘时再选择表现形式，记录明确要求或辅助表达的区别。直接记在已有笔记或章节草稿中，相关证据和章节结构稳定后再生成；仅要求计划时不提前出图。
- 成稿时按上表先判断内联代码图、原图或静态图。Mermaid 等内联图可以直接编写，不必为了简单示意启动静态后端。需要静态技术图时读取 [draw-diagram](../../draw-diagram/SKILL.md)，由它选择后端；定量实验、评测结果和科学曲线采用标准绘图工具。需要图片生成时读取相应技能，保留成本与用途判断，不为凑图调用。
- 交接当前任务、采用版本、图要回答的问题，以及有证据支持的组件／概念、关系／方向、必要标签和原始来源位置。未知或推断须在图或图注中说明，不能为完整布局编造组件、接口、数据流或实验数值；证据不足时先补查或简化表达。
- 内联图沿用 Markdown 的代码块与阅读器主题，不套用静态 SVG＋PNG 默认输出；静态图沿用入口技能的风格和所需格式，用户要求和项目已有风格优先。文件保存按 [自绘图的保存](delivery-policy.md#自绘图的保存) 执行，不使用入口技能的通用目录默认值。
- 图注注明“自绘”及原始依据，正文就近引用来源；自绘图是证据的表达，不作为新增独立证据。润色前核对图与正文的版本、术语、方向、标签和限定条件。代码图先做可用的语法／渲染检查，再在实际阅读器或明确说明的预览环境中检查中文、箭头、布局和可读性；静态图检查最终嵌入尺寸、间距与裁切。备用预览不能冒充用户实际阅读器验收。润色后根据 diff 复核受影响的图；纯措辞调整且图文一致时不重画。技术含义改变时返回成稿修订；未执行的检查不得标为通过。
- 配图失败时按所选后端的修复边界处理，不无止境重试。辅助图可改用文字或表格保留必要信息，移除未生成图的占位引用并说明未生成；用户明确要求或既定验收必需的图不能静默省略，未完成时如实说明缺口，不宣称交付已全部完成。报告 verify 的结构、证据一致性与文件检查不证明绘图检查、视觉复核或必需图验收已通过。

## 报告语言润色

所有对象类型的 light／full 报告在成稿后、最终 verify 前，读取项目内 [humanizer](../../humanizer/SKILL.md) 并执行其审读、改写和复查步骤。采用 embedded 模式，只将最终文本写回报告，不把中间草稿、问题清单或润色过程加入交付物。使用中性、准确的技术报告语气，删去空泛强调、重复总结和模板化表达；无需为追求风格而改动已经清楚的文字。

仅润色本次撰写的主报告及 Markdown 补充报告中的叙述。局部更新统一为“章节草稿 → 快照 → humanizer → 对照复核 → apply-update → 归档与状态同步 → verify”；不在 apply-update 后再润色整篇，不改未复核章节或扩大更新范围。普通措辞更正按用户指定范围编辑，无须另建调研任务；没有受管任务时用编辑器差异对照，不为润色强制启动新调研。中间文件放到当前任务 scratch/，遵循 [交付规范](delivery-policy.md) 管理。

- 保留结论、事实、数值、单位、版本、日期、比较口径、适用条件及证据强度；推断、unknown、冲突、限制与核心／非核心缺口不能因精简而消失，也不添加主观感受或未获证据支持的细节。
- 保持标题及其顺序、显式锚点、引用标记、链接目标、图片路径、图表编号、表格数据、公式、代码块、行内代码、命令与配置不变；可改善周围叙述，不能把引用移出已声明的章节。需要改变结构或技术含义时回到成稿／证据复核步骤处理。
- `report-note` 生成的开头和同目录的 `.meta.json` 由工具更新。润色时保留这两处，也保留原始文章、直接引文、证据笔记和结果配置。

### 保存快照并对照

受管任务使用 [润色对照脚本](../../research-common/scripts/research_polish.py)。命令从项目根执行，文件及快照路径均相对于项目根。新报告和根目录中的补充报告分别传入实际 Markdown 文件：

```text
python <skills_root>/research-common/scripts/research_polish.py snapshot --work-dir <work_dir> --file <output_dir>/report.md
```

局部更新先准备已登记章节的草稿，仅对草稿操作：

```text
python <skills_root>/research-common/scripts/research_polish.py snapshot --work-dir <work_dir> --file <work_dir>/scratch/sections.json
```

命令在本任务 scratch/polish/<快照ID>/ 保存 before.md／before.json 和 snapshot.json，返回 snapshot 相对路径。随后调用 humanizer 修改同一草稿，仅改 JSON 中的章节正文，不改键、范围或数据结构；不要润色 JSON 配置本身。修改后使用返回的实际快照目录：

```text
python <skills_root>/research-common/scripts/research_polish.py check --work-dir <work_dir> --snapshot <snapshot>
```
