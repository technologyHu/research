# 已有报告的局部更新

用于“补一节”“只更新某版本影响”“修订指定结论”等请求。先识别本次要复核的问题与章节，沿用原报告位置。一般措辞、错字、链接更正直接修改，无需重跑调研流程；涉及新证据或改变结论时使用以下流程。

## 建立更新范围

1. 创建新受管任务，`--output` 指向已有报告目录，必要时用 `--report` 指定现有文件名。只复核指定问题时，topic、goal、对象与字段描述本次范围；已有 full 任务可用且需要在原比较基础上追加对象／维度时，按 [任务管理](task-management.md#基于既有证据追加对象或维度) derive 继承有效证据，再扩展计划。单对象简短复查可用 light；需要处理证据冲突则用 full。
2. **在修改报告或关联文件前**保存基线并登记范围：

```text
python <skills_root>/research-common/scripts/research_task.py begin-update --work-dir <work_dir> --section "## 核心机制" --allow-file references/sources.md
```

`--section` 可重复，必须是报告中唯一、原样匹配的 ATX 标题（`##` 至 `######`），包含其子节；不能同时选父节和子节。重名标题先明确目标，不能自动采用第一个。Setext 标题、整篇重构或跨章节重排不适用这个辅助命令；按用户实际范围规划，不擅自改标题来凑通过。

新增顶层章节使用 `--add-section "## 新版本影响"`，标题必须尚不存在；辅助命令将其追加到文末。已有参考文章或图片只有明确列入 `--allow-file` 才可修改或移除，路径为报告目录下的精确相对路径；新来源 Markdown、正文引用的新图片仍受交付规范检查。允许文件不代表允许删除用户资料，仍须遵循用户任务范围。

临时 baseline/ 保存原文与文件散列，outline.update 记录范围和继承限制。不要手改基线、摘要或允许范围来接受无关改动。若确需扩大范围，先说明必要性，在原始报告状态上重新建立任务；并发修改时先协调当前文件，不覆盖其他人的改动。

## 复查与写入

按通常流程搜集证据，核对本次新增或受影响字段。输入指纹绑定问题、目标版本及研究口径，章节和基线属于独立交付设置；仅 begin-update 不要求重查语义未变的旧字段。派生任务继续检查全部计划对象，只有有效旧证据可沿用，不能通过 --item 省掉旧对象的检查。

未触及的旧章节继续保持原文、原版本与资料日期；旧核心和非核心缺口没有被本次解决时保留。原报告没有明确日期时如实标注未知，不用文件修改时间推断；能从原文核实时，可在 begin-update 传 `--baseline-date`／`--baseline-version` 明确其旧记录。

将新章节文本保存为当前任务 scratch/ 内的 UTF-8 JSON，键是登记的完整标题，值是包含同一标题的完整 Markdown 章节：

```json
{
  "## 核心机制": "## 核心机制\n\n复核后的分析、适用版本、资料日期与就近来源链接。"
}
```

在写入报告前，按 [报告语言润色](writing-policy.md#保存快照并对照) 保存草稿快照、调用 humanizer 润色章节正文，并用同一快照对照。顺序固定为章节草稿、快照、润色、对照复核、apply-update，不对未复核的整篇报告润色。

```text
python <skills_root>/research-common/scripts/research_polish.py snapshot --work-dir <work_dir> --file <work_dir>/scratch/sections.json
```

读取返回的 snapshot 路径，润色后先运行 check；仅在 valid=true 且人工确认语义和证据未改变时继续：

```text
python <skills_root>/research-common/scripts/research_polish.py check --work-dir <work_dir> --snapshot <snapshot>
python <skills_root>/research-common/scripts/research_task.py apply-update --work-dir <work_dir> --sections-file <work_dir>/scratch/sections.json
```

apply-update 只替换提供的已登记章节，并自动生成本次说明；未传入的已有章节保持不变，登记的新增章节最终必须存在。它不生成分析正文、不证明论证正确。写入前检查范围外变化和并发修改，通过后用当前任务 scratch/ 内的临时文件原子替换主报告；最终仍需人工阅读并运行 verify。

写入后按文章流程完成实际引用资料归档并同步链接，重新生成 report-note 更新本次说明；新格式报告按 [修订时间更新](task-management.md#报告修订时间与目录更新) 执行 stamp-report，使用返回的新 work_dir 执行 verify，旧布局继续原地校验。不要为刷新说明而重写未复核章节。快照和对照只保护这轮语言编辑，不替代最终 verify，也不证明论证正确。

也可以用编辑工具把已润色、已对照的章节写回报告，但保留完整正文并重新生成 report-note；verify 同样检查范围。不能用整篇重写、更换基线或覆盖润色前快照绕过检查。

## 如何解释完成度

报告状态显示“本次局部更新完整／部分完成”，只描述本次复查的问题，不代表整份报告已重新核实。说明中列出本次更新章节，保留未复核部分的旧版本、日期和缺口；连续局部更新继续继承更早的限制。

派生比较任务的完成度衡量更新后计划中的比较问题覆盖，包含被明确沿用的证据；不表示每个旧来源本次都重新访问。正文和来源索引区分旧资料与新增资料，保留原访问日期。新增对象使比较表或总体结论失效时，将它们纳入更新章节，不能只追加一个对象小节而保留失效的总体判断。

本次采用的版本不能覆盖未复核章节的版本。跨章节引用到已变化结论、原综述结论或比较表需要同步修订时，应将受影响章节一并纳入用户授权的范围；如果暂不复核，明确保留限制，不把可能矛盾的旧结论继续当成当前结论。

检查器核对章节边界、原文件散列、状态和来源引用，无法自动判断所有跨章节语义依赖。手工复核应重点检查旧结论是否因新证据而失效。最终仅交付原有允许文件和本次必要的文章、图片，baseline 和 sections.json 留在临时任务中。
