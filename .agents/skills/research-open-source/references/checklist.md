# 开源项目调研检查清单

- 是否明确仓库、许可、目标版本与 commit？当前文档与历史实现是否分开？
- 代码是否对应要求的论文／发布版本，版本映射是否有依据？各问题的核心、训练、推理、评测等角色由哪些仓库覆盖，有无缺口？
- 是否保留候选身份、原始依据、检索日期和采用／排除理由，恢复任务时复核变化？高 Star 或 README 自称官方是否被误用为充分依据？
- 源码可读性与运行状态是否分别记录，缺权重／数据／GPU 是否仅限制运行结论？访问受阻、未核实和未找到是否区分？
- 架构与系统边界是否由实际代码／接口支持，而非按通用术语猜测？
- 能否完整追踪代表用例及其错误、重试、状态更新与副作用？
- 关键实现结论是否附固定版本的代码路径与精确位置？
- 代码理解是否绑定实际目标 checkout 和未提交变更，回写当前研究字段，并区分原始源码证据与后端推断？已有图谱的版本和覆盖范围是否核对？
- 是否区分测试文件存在、官方报告通过和本次实际执行通过？
- 是否按 [素材类型](../../research-common/references/writing-policy.md#值得纳入的图与演示类型) 检查 README 和文档中的架构、部署、流程及输出示例？项目有前端或交互入口时，是否按需引用有解释价值的界面与演示，并注明版本、来源及实际核验范围，而非把他人演示当作本次运行结果？
- 性能、资源和安全判断是否有适用条件及证据，缺少 benchmark 是否明确？
- 是否把闭源引擎、公开类型、开源集成包和教学模型清楚区分？
- 本次只保留规定交付，报告不再承诺已经清理的源码、模板或实验文件仍存在？
- 涉及对象评估时，是否按 [开源标准](selection-criteria.md) 核对工程参考地位、实际生态采用，以及发起／维护、公司／基金会、项目资源和治理角色？项目影响与关联公司融资是否分开？
