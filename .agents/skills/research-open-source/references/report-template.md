# 开源项目技术报告结构

先选择 [项目类型](project-types.md)，再按研究目标裁剪。聚焦关键机制，不强制统计所有文件或填写与项目无关的运维章节。

| 默认字段 id | 章节／问题 |
| --- | --- |
| identity | 定位、用户、解决问题、许可、仓库、版本／提交和资料日期 |
| architecture | 系统边界、架构风格、模块职责、依赖与设计取舍 |
| core_flow | 一个代表性用例如何从入口经过关键模块到结果，包含错误路径 |
| implementation | 关键算法、数据结构、状态、协议或存储机制，固定代码锚点 |
| extension | API、配置、插件、钩子、扩展点及其约束 |
| quality | 已有测试与质量机制、实际执行情况、安全与可靠性边界 |
| operations | 有关时说明部署、性能证据、资源成本与运维要求 |
| ecosystem | 版本演进、社区与集成；指标附采集日期，不把仓库热度当成效果 |
| assessment | 优势、局限、适用场景、与研究目标相关的借鉴点 |

源码分析采用“行为 → 入口 → 关键路径 → 数据／状态 → 结果与失败边界”组织，避免把文件列表当作实现分析。至少对关键结论给出固定提交、路径与行号。

架构图、流程图和时序图按需要使用。示例标明来源和是否执行。比较模式先解释共同问题和接口边界，再给实现差异；闭源核心与开源集成包分别标注。
