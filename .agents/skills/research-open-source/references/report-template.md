# 开源项目技术报告结构

标题下使用工具生成的简短说明，正文按下列结构组织。见 [报告开头](../../research-common/references/writing-policy.md#报告开头)。

先选择 [项目类型](project-types.md)，再按研究目标裁剪。聚焦关键机制，不强制统计所有文件或填写与项目无关的运维章节。

涉及选题、权威性／影响力或维护与资金背景时，按 [开源项目评估标准](selection-criteria.md) 在 identity／ecosystem／assessment 中说明发起与维护、治理和资源、工程可信度及生态采用。相关公司融资归公司，项目采用归项目；局部源码问题不强制补全商业调查。

| 默认字段 id | 章节／问题 |
| --- | --- |
| identity | 定位、用户、解决问题、许可、仓库、版本／提交和资料日期 |
| architecture | 系统边界、模块职责、运行位置、依赖与设计取舍 |
| core_flow | 代表性场景由谁触发、由谁执行、结果交给谁，以及失败时可观察到什么 |
| implementation | 关键算法、数据结构、状态、协议或存储机制，固定代码锚点 |
| extension | 外部调用方可使用的接口或扩展机制，以及输入、输出和使用条件 |
| quality | 已有测试与质量机制、实际执行情况、安全与可靠性边界 |
| operations | 有关时说明部署、性能证据、资源成本与运维要求 |
| ecosystem | 版本演进、社区与集成；指标附采集日期，不把仓库热度当成效果 |
| assessment | 优势、局限、适用场景、与研究目标相关的借鉴点 |

对象容易混淆时，先用一个实例说明谁管理什么、哪些对象可以共享、一次运行选用哪个实例，以及配置在哪里生效。对跨进程或跨设备的交互，标出每端的运行位置和直接调用方。

按执行链路归纳场景。入口相似但执行方、状态变化或结果去向不同的用例可分开讲；仅输入内容不同、处理过程相同的用例可作为同一场景的示例。沿代表用例追到可观察的结果及失败边界。若经过异步提交或多端协作，说明各次返回分别证实了什么。例如队列返回任务 ID 能证实已受理，任务是否完成还要看执行记录或产物。关键结论给出固定提交、路径与行号。

项目同时提供用户操作与编程接口时，分别回答两类读者的问题。使用说明写操作入口和可见效果；集成说明选一个实际外部调用方，写清所用接口、输入、处理模块、返回值或事件，以及必要权限和失败表现。根据公开契约和对应版本的实现判断哪些能力对外可用；仅在内部调用链中出现的函数或服务归入实现说明。

架构图、流程图和时序图按需要使用。示例标明来源和是否执行。比较模式先解释共同问题和接口边界，再给实现差异；闭源核心与开源集成包分别标注。

项目存在前端或交互入口时，可按 [界面与演示素材](../../research-common/references/writing-policy.md#界面截图与演示素材) 复用相关截图和演示 GIF，说明代表用例如何操作、状态如何变化以及结果在哪里。没有界面或素材没有新增解释价值时保留文字和代码分析，不要求为了配图运行项目。
