> 上一篇我把"全托管研发体系"搭起来了。但说到底，体系再花哨，底层还是 Coding Agent 在干活。最近一周我在 Multica 上轮着用了 5 款 Coding Agent——聊聊真实感受，不写软文。

## 起：体系搭好了，Agent 没选对，全白搭

上一篇里我把整套全托管研发体系讲了一遍：飞书提需求 → 产品经理拆任务 → 开发小队编码 → 评审测试 → 运维发布。中途 autopilot 每半小时巡检一次，我只在飞书上看进度。

听起来很美好对吧？**但实际跑起来你会发现一件事：底层跑任务的 Coding Agent 不一样，整套体系的体感、成本、稳定性，能差出三条街。**

比如某个 Agent，单任务 token 烧得飞起，钱包冒烟；某个 Agent 缓存命中率极高，省钱省到笑；还有一个 Agent，任务完成率低到让人想砸键盘——巡检日志里一半都是它超时挂掉的。

所以问题就来了：**既然 Coding Agent 是这套体系的"发动机"，那我到底该 Pick 哪个？**

过去这一周，我轮着把 5 个主流 Coding Agent 都跑了一遍，今天就把真实数据、真实踩坑、真实解法，毫无保留地讲给你。

> **Coding Agent** 简单解释一下：它是真正"动手写代码、跑命令"的那个 AI 工具。在 Multica 体系里，PM、架构师这些角色背后都接了不同的 Coding Agent 来执行。

## 一、我跑过的 5 个 Coding Agent，速览表

先上一张我整理的"实战表"：

| # | Coding Agent | 优势 | 劣势 | 硬伤 |
| --- | --- | --- | --- | --- |
| 1 | Codebuddy | 任务完成率高 | token 杀手 | 无效 prompt 惊人 |
| 2 | OpenCode | 模型兼容性好 | 完成率、缓存命中率一般 | 暂无硬伤 |
| 3 | Codex | 任务完成率极高 | 模型限制（至少要支持 responses） | 暂无 |
| 4 | Pi Agent | 缓存命中率惊人，DS vs Flash 干到 97% 毫无压力 | 任务完成率极低 | find 命令经常导致任务阻塞 |
| 5 | DSH（DeepSeek Harness） | 缓存命中优秀 | 预览版，更新较快 | 暂无 |

**一句话总结这五个：**

* **Codebuddy**：能干，但贵。
* **OpenCode**：平庸但稳。
* **Codex**：能干、要求也高。
* **Pi Agent**：最省钱，但最容易翻车。
* **DSH**：潜力股，等它稳定。

下面我挑重点，把每个 Agent 的真实使用感受详细讲一下。

## 二、逐个点评：它们各自最适合干什么

### 1. Codebuddy：能打，但 token 烧得我肉疼

Codebuddy 是我最早用来初始化 Multica 环境的 Coding Agent，**任务完成率确实高**，复杂任务交上去基本都能干完。

但它有个让我肉疼的特点：**token 消耗是同行里的"销冠"**。

我用 AgentLens（Multica 里的观测工具，可以看每一次 Agent 调用的详细 prompt 和上下文）看了一眼它跑任务的过程，发现每一轮任务的 prompt 里基本都会包含：

* Multica 的 system prompt
* Codebuddy 自己的 system prompt
* Issue 上下文（**而且是叠加的，不是覆盖**）

每一次新上下文进来，不是把老的换掉，而是叠在上面。**这就是它成为 token 杀手的核心原因**——越聊越胖，每一轮都比上一轮贵。

> **踩坑提醒**：如果你看重成本，Codebuddy 不是首选。适合"贵但能干"的场景，比如关键路径上的复杂任务。

实拍一下 AgentLens 里 Codebuddy 的上下文结构，每跑一轮都叠一层：

![Codebuddy 上下文叠加：multica system prompt + codebuddy system prompt + issue 上下文叠加](Codebuddy 上下文叠加：multica system prompt + codebuddy system prompt + issue 上下文叠加)

### 2. OpenCode：万金油，但没亮点

OpenCode 是我配合 Multica 用的第一个 Coding Agent，**最大优点是模型兼容性极好**——主流模型几乎都能接，对运行环境也没什么挑剔。

但它的问题也很明显：**完成率和缓存命中率都"中等偏上"，没有任何特别亮眼的地方。**

适合什么场景？

* 你想快速验证方案、不想折腾环境兼容性 → 用它。
* 你对成本没有特别敏感的诉求 → 用它。
* 你要的是"稳定但别给我惊喜" → 用它。

> **踩坑提醒**：别指望它在"极致省钱"或"高完成率"上有突破。它是水桶型选手，不是尖子生。

### 3. Codex：完成率天花板，但模型挑剔

Codex 是第二天我换上的 Coding Agent，主要是看中了它的 harness（**harness 就是"驾驭模型的整套机制"，包括 prompt 组织、上下文管理、错误恢复等**）做得好。

实际跑下来，**任务完成率是我用过这几个里最高的**，复杂任务、跨文件改动、连续多步操作，都能干得比较稳。

但它有个硬门槛：**模型必须支持 responses 接口**。这意味着你不能随便给它塞个模型，得挑那些新一代 API 协议的。

> **踩坑提醒**：用 Codex 前先确认你的模型支持 responses API，否则接不上。它适合"对完成率有极致要求"的场景，比如生产项目的核心开发。

### 4. Pi Agent：缓存命中率之王，但容易翻车

Pi Agent 是第四天我引入的。

**最大的惊喜是它的缓存命中率**。我用 DeepSeek V3.1 Flash 这个模型测试，缓存命中率干到 **97%**——基本上每 100 token 里有 97 个是从缓存里读的，**几乎不花钱**。

如果你也在意成本，看到这个数字应该会心动。

**但——它也是我这次踩坑最深的。**

打开 Multica 任务分析一看，Pi Agent 的失败率**遥遥领先**。继续往下查原因，发现它特别喜欢调用 `find` 命令，而且经常挂死。

我后面查了查，搞清楚了原因：Pi Agent 用的 bash 工具**没有 wall-clock timeout（超时机制）**，而 `find` 一旦撞上 `~/Library`、`node_modules`、`.git` 这种大目录，就会无限递归，**直接挂到天荒地老**。

> **踩坑提醒**：Pi Agent 缓存无敌，但如果你不约束它，它会用 find 把你的任务拖崩。**别裸用，必须配 AGENTS.md**（下面会讲怎么配）。

直接看图——Pi Agent 在我项目里的失败率是这样的：

![Pi Agent 失败率遥遥领先](Pi Agent 失败率遥遥领先)

### 5. DSH（DeepSeek Harness）：潜力股，等稳定

DSH 是 DeepSeek 最近发布的 harness。**缓存命中优秀**这一点跟 Pi Agent 有得一拼，但因为还在预览版，更新比较快，体感上还有不少小毛病。

我的判断是：**值得关注，先小范围试水，别直接上生产**。

## 三、踩坑实录：Codebuddy 和 Pi Agent 我怎么救回来的

光列优缺点没用，**关键是遇到硬伤你怎么救**。下面这两个解法，是我真正在生产环境里跑出来的。

### 坑 1：Codebuddy 的"token 滚雪球"

Codebuddy 每一轮任务的上下文都在叠加，越跑越胖。这个没什么"银弹"解法，但有几个缓解动作：

* **定期清理上下文**：在 Multica 控制台里，把跑得太长的会话手动 close，让新任务从干净上下文起步。
* **任务粒度拆细**：让 PM 把任务拆到"一件事一个会话"，别一个大任务来回聊 200 轮。
* **预算控制**：在 Multica 里给每个 Agent 设 token 预算上限，超了自动停，别等账单来了再哭。

> 这一条其实跟第三篇 Token 体检的结论是相通的：**会话越短，越省钱**。

### 坑 2：Pi Agent 的"find 挂死"

Pi Agent 失败率高的根因就两个：bash 没超时 + 滥用 find。

打开任务分析一看，几乎全是执行 `find` 这类命令超时挂死——而且频率极高，Pi Agent 特别爱调 find：

![Pi Agent 任务分析：find 命令频繁超时](Pi Agent 任务分析：find 命令频繁超时)

![Pi Agent find 超时细节](Pi Agent find 超时细节)

我在 `~/.pi/AGENTS.md` 里写了一段强制约束，**实测下来效果立竿见影**：

```
## bash 调用规范（强制）  
  
1. **禁用 find** 除非满足以下全部条件：  
   - 显式传 `-maxdepth 6`  
   - 对大目录（~/Library、node_modules、.git、Caches）用 `-prune` 排除  
   - 命令必须显式带 `timeout 30s`  
  
2. **禁止在 ~ 下启动 pi 工作**：Library/Caches 会拖垮任何递归命令。  
   必须 `cd` 到具体项目目录，或用 `pi --cwd <项目路径>` 指定 cwd。  
  
3. **所有 bash 调用必须显式传 timeout**：  
   - 默认 60s  
   - 查找类 30s  
   - 构建/测试类 120–300s  
  
4. **命令组合用 &&，不用 ;**：前一步失败就别继续跑。  
  
5. **sudo 一律拒绝**：需要 sudo 的，告诉用户手动跑。
```

这套规则加完之后，**Pi Agent 的失败率从最高的那一档，直接降到了接近 Codex 的水平**。缓存命中率的优势也保住了。

> 这里有个通用经验：**AI Agent 的硬伤，往往不是因为它笨，而是因为它的"工作规范"没写清楚**。给它立规矩，它就能发挥该有的水平。

## 四、我的真实推荐：按场景选，别迷信"全能选手"

写到这里你应该发现了：

**没有"最好"的 Coding Agent，只有"最适合你场景"的。**

给你一张决策清单，对号入座：

* **要省钱、要大规模跑** → Pi Agent（前提是配好 AGENTS.md）
* **要完成率、要稳定交付** → Codex
* **要兼容性强、想省心** → OpenCode
* **要极致任务完成、不差钱** → Codebuddy
* **想试新东西、愿意接受更新频繁** → DSH

我现在的组合是：**Codex 跑核心开发 + Pi Agent 跑轻量任务**。

核心的、复杂的、对稳定性要求高的任务，让 Codex 上；日常的、轻量的、对成本敏感的任务，让 Pi Agent 上。两个各司其职，整套体系既稳又省。

## 五、避坑清单（建议你收藏）

最后把这次踩过的坑总结成 5 条，列给你：

1. **不要在 ~ 目录下启动 Agent**。Library/Caches 会拖垮任何递归命令，必须指定 cwd 到具体项目。
2. **所有 shell 命令必须显式带 timeout**。默认 60s，查找 30s，构建/测试 120–300s。
3. **禁用 find 用作"全局搜索"**。除非带 `-maxdepth` + `-prune` + `timeout 30s`，否则必挂。
4. **Agent 的硬伤，大半可以靠 AGENTS.md 救回来**。立规矩 = 给它"工作手册"，比换模型更治本。
5. **任务粒度拆细，别让会话滚到 200 轮**。一轮贵一轮，越聊越胖。

## 写在最后

这次轮着跑 5 个 Coding Agent，我最大的感受是：

**Coding Agent 不是一个"工具"，更像一个"新同事"**。

它有自己的脾气、长处、短板，你要的不是"找一个最厉害的"，而是"管好一群各有特点的"。

这跟 Multica 那套"产品经理 + 开发小队"的思路其实是一回事——**靠体系，不是靠单点英雄**。

下一篇我打算接着聊——**Agent 团队协作时，怎么避免它们互相拆台、避免 PM 越权乱派活**。点个关注，下次见。
