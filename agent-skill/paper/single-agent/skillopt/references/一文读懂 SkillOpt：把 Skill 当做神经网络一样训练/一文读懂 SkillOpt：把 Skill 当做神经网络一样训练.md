SkillOpt 把 `SKILL.md` 当成"可以训练的参数"，但它不修改模型权重，而是根据 Agent 的成功和失败轨迹，反复对 Skill 文字做小范围的增、删、改，并用独立验证集决定是否接受修改。

也就是：

> 模型不训练，训练的是给模型看的操作手册。

官方称之为 **text-space optimization（文本空间优化）**。项目主页：microsoft.github.io/SkillOpt/，论文：arxiv.org/abs/2605.23904。

---

## SkillOpt 的核心原理

假设当前 Skill 是 S\_t，Agent 模型及执行框架都是固定的。目标可以简单表示为：

**S\* = argmax E[R(Agent(x, S))]**

其中：

* • **S**：Skill 文档
* • **x**：任务样本
* • **R**：任务得分或是否成功
* • Agent 模型权重始终不变
* • 优化对象只有 Skill 文本

整个过程相当于把深度学习训练机制"翻译"到了文本空间：

| 深度学习训练 | SkillOpt 中对应的东西 |
| --- | --- |
| 模型参数 | Skill 文档 |
| 前向运行 | Agent 执行任务 |
| Loss / Reward | 任务评分 |
| 梯度 | 成功和失败的执行轨迹 |
| Optimizer | 用于分析轨迹、修改 Skill 的另一个 LLM |
| Learning rate | 每轮允许修改多少文字 |
| Mini-batch | 一小批执行轨迹 |
| Validation set | 独立验证集 |
| Momentum / 慢变量 | 跨 epoch 的反思和 meta-skill |
| Checkpoint | 当前最好版本 `best_skill.md` |

需要强调：所谓"轨迹是梯度"只是一种类比。它没有计算真正的数值梯度，而是让优化器模型从轨迹中判断"哪里出了问题、Skill 应该怎么改"。

## 完整工作流程

### 1. 固定 Agent，运行当前 Skill

一个被冻结的目标 Agent，携带当前 Skill S\_t，在训练集任务上执行。

每次执行都保存：

* • Agent 的行动过程
* • 工具调用
* • 中间结果
* • 错误信息
* • 最终答案
* • 任务得分

这些合称为 **rollout trajectories，运行轨迹**。

例如，一个电子表格 Skill 可能写着：

> 修改单元格后检查公式是否正确。

实际轨迹却显示 Agent 经常只检查公式文本，没有触发重新计算。优化器便可能发现一个系统性缺陷：

> Skill 缺少"重新计算并验证最终数值"的明确步骤。

### 2. 将轨迹切成多个 mini-batch

所有轨迹不是一次性扔给优化器，而是分成 K 个小批次。

每个 mini-batch 由优化器模型独立分析，提出最多 L 个原子修改：

* • **ADD**：增加规则
* • **DEL**：删除无效或有害规则
* • **REP**：替换原有规则

使用 mini-batch 的原因与机器学习类似：减少一次输入过长的问题，也让不同批次独立暴露不同的失败模式。

### 3. 合并修改建议

不同批次可能提出重复或冲突的修改，例如：

* • 批次一：必须始终调用搜索工具
* • 批次二：简单问题不要调用搜索工具
* • 批次三：仅在信息不确定时调用搜索工具

SkillOpt 会：

1. 1. 去重；
2. 2. 解决冲突；
3. 3. 对修改排序；
4. 4. 根据修改预算 L\_t 截断。

最后不会让优化器随意重写整份 Skill，而只应用有限数量的修改。

这就是它所谓的 **bounded edits（有界修改）**。

### 4. 生成候选 Skill

Modifier 将选中的修改应用到当前 Skill：

**S\_t →（有界修改）→ S\_{t+1}^candidate**

有些区域还可以设置为受保护区域，禁止优化器随意修改，例如：

* • Skill 的身份和目标
* • 安全约束
* • 输出协议
* • 必须遵守的业务规定

### 5. 用独立验证集决定是否接受

候选 Skill 不会直接覆盖当前 Skill，而是先在独立验证集上运行。

只有验证成绩严格提高，候选版本才会成为新的当前 Skill：

**如果验证分数提高 → 接受候选版本；否则 → 保持当前版本不变。**

这一步是 SkillOpt 最关键的机制之一。它防止优化器：

* • 只针对某几个训练样本写规则；
* • 因一次偶然失败做过度修改；
* • 不断往 Skill 里堆补丁；
* • 把一个局部问题修好，却破坏其他任务。

测试集在整个优化过程中锁定，最终报告时才使用，避免把测试集也"训练"进去。

### 6. 记录被拒绝的修改

验证不通过的修改不会直接遗忘，而是进入：

> rejected-edit buffer，被拒修改缓冲区

后续优化器会看到：

* • 哪些修改已经尝试过；
* • 为什么失败；
* • 哪类修改不要重复提出。

它相当于文本优化过程中的"负反馈历史"。

### 7. 跨 epoch 做慢速反思

完成一个 epoch 后，系统比较：

* • 上一个 epoch 的 Skill
* • 当前 epoch 的 Skill
* • 同一批样本在两个 Skill 下的轨迹

然后把结果归纳成四类：

* • 有改善的案例
* • 退步的案例
* • 持续失败的案例
* • 稳定成功的案例

再生成两种长期信息：

1. 1. **慢更新内容**：补充到下一轮 Skill 修改中；
2. 2. **Optimizer meta-skill**：告诉优化器以后应如何修改 Skill。

meta-skill 记录的不是具体业务规则，而是优化经验，例如：

* • 哪类修改通常有效；
* • 哪类修改经常失败；
* • 还有哪些长期失败模式；
* • 应该更倾向增加规则，还是删除冗余规则。

因此 SkillOpt 实际上有两层学习，形成一个闭环：

**执行任务 → 优化 Skill 内容 → 验证是否提升 → 更新当前 Skill → 总结跨轮优化经验 → 改进优化器的修改策略 → 重新执行任务**

## 数据集的三重划分

| 角色 | 功能 |
| --- | --- |
| 训练集 | 提供运行轨迹，暴露"为什么失败"的证据 |
| 验证集 | 作为更新门槛，决定修改是否值得接受 |
| 测试集 | 最终报告前锁定，只负责最终评价 |

这种划分至关重要：训练集提供证据，验证集做决策，测试集保持独立。

## 图中关键概念翻译速查

**小批次优化区域**

* • mini-batch：小批次
* • Optimizer model：优化器模型
* • L atomic edits per mini-batch：每个小批次最多提出 L 个原子修改
* • ADD / DEL / REP：增加／删除／替换

"原子修改"指一次尽量独立、具体的小修改，而不是整篇重写。

**修改合并区域**

* • Batch-level merge：批次级合并
* • deduplicate + resolve conflicts：去重并解决冲突
* • Rank/clip by edit budget L\_t：按修改预算排序并截断
* • LR schedule: decay L\_t：学习率计划——逐渐减小 L\_t

这里的 LR（Learning Rate）不是数值梯度的学习率，而是"这一轮最多允许对 Skill 改多少"。前期可以改得多一些，后期预算逐渐减小，让 Skill 趋于稳定。

**生成候选与验证**

* • candidate skill：候选 Skill
* • Modifier：修改器
* • bounded text update：有界文本更新
* • Validation gate：验证门槛
* • accept / reject：接受／拒绝
* • rejected-edit buffer：被拒修改缓冲区
* • best\_skill.md：最佳 Skill 文件

## 它与"让 LLM 直接改写 Skill"有什么不同？

这是理解 SkillOpt 的关键。

| 普通做法 | SkillOpt |
| --- | --- |
| 把几个失败案例交给 LLM | 收集带评分的完整轨迹 |
| 一次性重写 Skill | 只允许增、删、替换等有界修改 |
| 修改幅度不可控 | 有文本学习率和衰减计划 |
| 修改后直接使用 | 必须通过独立验证集 |
| 失败修改被遗忘 | 保存到被拒修改缓冲区 |
| 每轮彼此独立 | 跨 epoch 总结长期规律 |
| 容易越改越长 | 排序、截断并控制修改预算 |
| 通常只优化 Skill | 同时优化"怎样优化 Skill"的 meta-skill |

所以它真正的新意不是"LLM 会反思"，而是：

> 把原本松散的"执行—反思—改提示词"，包装成一个具有批次、步长、验证、拒绝历史和跨轮状态的可控优化算法。

## 适用场景与主要限制

SkillOpt 最适合以下场景：

* • 任务可以重复执行；
* • 每次执行能得到比较可靠的分数；
* • 有几十到几百个代表性任务；
* • Skill 主要描述稳定的操作流程；
* • 不方便微调模型权重；
* • 希望最终产物仍然是可读、可移植的 `SKILL.md`。

它的主要限制也很明显：

**1. 评分器必须可靠。** 如果验证分数不可信，系统会把 Skill 优化到错误目标上。

**2. 成本主要发生在优化期。** 同一批任务需要反复运行目标模型和优化器模型。不过部署后只需要加载最终 Skill，不增加额外模型调用。

**3. 仍然可能对验证集过拟合。** 验证集反复充当更新门槛，本质上也参与了模型选择，所以最终仍然需要锁定测试集。

**4. 更像自动化实验框架，不是神奇的自进化。** 真正决定效果的仍然是任务集覆盖度、轨迹信息、评分标准和优化器模型的分析能力。

**5. 对不可验证的开放任务帮助有限。** 例如写作风格、战略判断、情感沟通，很难定义稳定的自动评分，Validation gate 也就不够可靠。

对于"如何把分析新技术的方法沉淀成可复用 Skill"这件事，SkillOpt 可以用来优化其中**可验证的流程部分**，例如：

* • 是否检查了官方文档和论文；
* • 是否覆盖架构、扩展性、活跃度和迁移成本；
* • 引用是否真实；
* • 比较表是否完整；
* • 最终推荐是否与证据一致。

但"洞察是否深刻""推荐是否有判断力"仍然很难完全自动评分。SkillOpt 能优化流程纪律，却不能自动生成一个可靠的价值判断体系。
