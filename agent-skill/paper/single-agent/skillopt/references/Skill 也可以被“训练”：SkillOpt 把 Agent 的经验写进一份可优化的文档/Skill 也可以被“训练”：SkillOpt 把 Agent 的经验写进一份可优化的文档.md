你可能已经见过很多“会自我改进”的 Agent：它跑完一次任务，复盘一下；失败了，再重写一版 prompt；最后把经验保存成一个 skill。

问题是，这类改进往往更像“改作文”，而不是训练。一次失败就可能触发大段重写，原本有效的规则被覆盖，偶然的经验被写进 skill，连续几轮之后，系统甚至不知道究竟是哪一次修改带来了提升。

SkillOpt 的切入点很直接：如果 skill 是 Agent 的程序性知识，那么 skill 文档本身就应该成为可优化的外部参数。

这篇论文最值得关注的地方，不是又提出了一个 skill 格式，而是给 skill 的演化加上了类似深度学习训练的纪律：有训练数据、有验证集、有“学习率”、有拒绝更新的机制，也有保存长期经验的慢更新。



01

先说结论：它把“改 skill”变成了“训练 skill”

SkillOpt 的核心判断可以概括成一句话：Agent 不一定要改模型权重，先把它的外部 skill 训练好，也能获得稳定的领域适应能力。

论文在 6 个 benchmark、7 个目标模型和 3 种执行环境上测试了这一想法。在 52 个“模型 × 任务 × harness”评测单元中，SkillOpt 全部取得最佳或并列最佳结果。

以 GPT-5.5 的直接对话结果为例：



* SearchQA：77.7% → 87.3%
* SpreadsheetBench：41.8% → 80.7%
* OfficeQA：33.1% → 72.1%
* LiveMathematicianBench：37.6% → 66.9%
* ALFWorld：83.6% → 95.5%

平均提升 23.5 个百分点。在 Codex 和 Claude Code 这类带工具的执行环境中，平均提升分别是 24.8 和 19.1 个百分点。

数字很漂亮，但更重要的问题是：它到底做了什么，为什么不是一次普通的 prompt 重写？

02

SkillOpt 的训练循环，和模型训练有什么相似之处？

SkillOpt 把 Agent 的目标模型冻结，只训练一份自然语言 skill。每轮流程大致如下：



1. 让目标模型带着当前 skill 执行一批任务，记录完整轨迹；
2. 把成功和失败的轨迹分开，交给另一个更强的 optimizer model分析；
3. 让 optimizer 提出结构化的增删改编辑；
4. 合并重复或冲突的建议，并限制本轮最多能改多少处；
5. 用验证集测试新 skill，只有分数严格提升才接受；
6. 把被拒绝的修改记录下来，作为后续的负反馈。

最后，系统只导出验证集表现最好的 `best_skill.md`。部署时不需要再次调用 optimizer，也不需要修改目标模型权重。

这个设计里有几个关键的“训练化”改造。

第一，文本编辑预算就是自然语言版的学习率

普通的 skill 演化常见做法是：把失败轨迹和旧 skill 一起交给模型，然后让它“重新写一版更好的 skill”。这种做法的问题是更新步长不可控。模型可能只想修一个规则，却顺手删掉了十条有效经验。

SkillOpt 不让模型无限重写，而是把修改拆成 `ADD`、`DELETE`、`REPLACE` 等原子编辑，再设置一个编辑预算。比如本轮最多接受 4 个修改，候选编辑超过预算时，先按预期收益排序，再截断。

这就像给文本参数加了一个学习率：每次只允许 skill 朝新的方向移动有限距离。它牺牲了一点“看起来很彻底”的改写自由，但保住了训练过程的连续性。

当然，skill 不是连续向量，文本编辑也不是梯度下降。这里的类比是操作层面的：编辑预算控制更新幅度，验证集决定更新是否值得保留。

第二，验证集门控，阻止“听起来合理”的错误经验积累

语言模型很擅长解释失败，但一个解释得通的原因，不等于真的能提升任务表现。

因此 SkillOpt 不会因为 optimizer 给出的建议很有道理，就直接写进 skill。每个候选版本都必须在 held-out selection split 上重新执行。只有分数严格高于当前版本，更新才会被接受；平局也拒绝。

这一步看似保守，实际上是整套方法的安全阀：反思负责提出假设，验证集负责决定假设有没有用。

这里的“分数”并不是 optimizer 给 skill 文本打的主观分，也不是另一个模型凭语言感觉评估“这段规则写得好不好”。它来自目标模型带着这份 skill 实际执行任务后的结果，再交给 benchmark 自带的 evaluator 判分：问答任务看准确率，表格任务看硬分数或完成率，数学任务看答对率，ALFWorld 看环境任务是否成功。也就是说，评估对象是“带着这份 skill 的 Agent 能不能把任务做对”。

论文把数据分成三部分：训练集用来生成执行轨迹、提出 skill 修改；验证集用来筛选候选版本；测试集在整个优化过程中锁定，只在最后报告结果。比如当前 skill 在验证集上平均得分为 72，新版本得到 74，修改才会被接受；如果只有 72 分或下降到 70 分，就拒绝。这样做的目的，是避免 skill 只记住训练样本，也避免用测试集反复挑选出一个看似很高、实际泛化很差的版本。

论文的消融实验也支持这一点。去掉验证和受控更新后，skill 更容易积累局部修补，最终效果明显下降。验证集不是最后才看的报表，而是每一步编辑的选择门。

第三，被拒绝的修改不会浪费，它们会变成负反馈

很多自动优化系统只保存“成功版本”，失败尝试被直接丢弃。SkillOpt 则维护一个 epoch 内的 rejected-edit buffer，记录哪些修改被试过、导致了多少分数下降。

后续 optimizer 再提出方案时，会同时看到这些失败经验，从而避免反复尝试同一类错误改动。

这让 skill 优化不只是“从成功案例中总结规则”，还可以回答一个更实际的问题：哪些看似合理的规则，在这个 Agent 身上已经被证明会带来伤害？

第四，用慢更新保存跨轮次的长期规律

单个 rollout 只能反映眼前的失败。比如某一次任务中，Agent 选错了一个文件，最简单的修补可能是把正确文件名写进 skill。但这很可能只对当前样本有效。

SkillOpt 在每个 epoch 结束时，会比较上一轮和当前 skill 在同一批训练样本上的表现，把变化归类为：改进、退化、持续失败和稳定成功。然后由 optimizer 写出一段更长期的指导信息，放进受保护的 slow-update 区域。

这有点像训练里的 momentum：快速更新处理当前问题，慢更新提炼跨轮次仍然成立的规律。更关键的是，慢更新区域不能被普通的 step-level 编辑覆盖，避免一次局部修补抹掉长期经验。

03

真正的亮点：它学到的不是答案，而是做事方式

如果一个 skill 只是把训练样本里的答案、文件名和固定步骤抄进去，它在 benchmark 上涨分并不奇怪，也没有太大迁移价值。

SkillOpt 的迁移实验因此很关键。

在跨模型实验中，GPT-5.4 上训练出的 SpreadsheetBench skill，迁移到 GPT-5.4-mini 后仍然提升 9.4 个百分点，迁移到 GPT-5.4-nano 后仍提升 3.0 个百分点。LiveMath 的 skill 在更小模型上也保持正收益。

跨 harness 的结果更有意思：在 Codex 中训练的 SpreadsheetBench skill，迁移到 Claude Code 后，从 22.1% 提升到 81.8%，增加 59.7 个百分点；反向迁移也有 43.6 个百分点的提升。

这说明学到的可能不是某个具体 API 的调用方式，而是更高层的程序性规则，例如先检查工作簿结构、区分公式和静态值、完成后做结果核验。执行环境变了，这些规则仍然有用。

当然，跨 benchmark 的迁移要弱得多。OlympiadBench 训练的数学 skill 迁移到 Omni-MATH，三个模型规模上仍然都是正收益，但提升只有 1.3 到 3.7 个百分点。换句话说，skill 的迁移边界也是真实存在的：任务越相近，程序性知识越容易复用。

04

52 个单元全胜，但不要把它理解成“skill 已经解决了 Agent 适应问题”

这篇论文的结果很强，但有三个地方需要保持清醒。

第一，SkillOpt 依赖可靠的评分信号。它最适合有 exact match、执行检查、自动 verifier 或其他可重复评价方式的任务。对于科研写作、开放式分析和多目标决策，什么叫“严格提升”并不容易定义，验证门可能需要人工或另一个评审模型参与。

第二，部署便宜，不等于训练便宜。最终的 `best_skill.md` 只有 379 到 1,995 个 token，通常经过 1 到 4 次被接受的编辑就能得到。但训练阶段仍需要大量 rollout 和 optimizer 调用。论文报告的训练 token 数从 2,080 万到 2.138 亿不等。只有当同一个 skill 会被反复复用时，这笔成本才容易摊薄。

第三，单个 skill 不是万能的领域知识库。论文当前优化的是“一个目标域对应一份 skill”，而不是一个可动态路由的 skill library。面对高度异质的任务集合，一份文档可能既不够覆盖，也不适合继续堆规则。

还有一个隐含风险：skill 可能把训练分布中的启发式固化下来。论文做了跨模型、跨 harness 和跨 benchmark 测试，这是很好的开始，但仍不能替代在真实数据上的独立验证。

05

我的判断：SkillOpt 的价值，不在于让 Agent “自己改自己”

“自我进化 Agent”这个说法很容易让人想到一个不断自我重写、最终变得无所不能的系统。但 SkillOpt 实际上走的是一条更克制、也更工程化的路线：

让模型提出修改，让数据决定修改是否留下；让快速编辑解决眼前失败，让慢更新保存长期规律；让训练阶段变复杂，让部署阶段保持简单。

这套思路对生信 Agent 尤其有启发。

很多生信任务并不缺“知道应该做什么”的模型，真正缺的是稳定的过程约束：先确认物种和参考版本，再检查输入文件，再执行分析，最后核对输出是否和假设一致。把这些过程性规则写进 skill 之后，关键问题就不再是“模型能不能想出一个漂亮的方案”，而是“哪些规则经过真实运行证明有效”。

SkillOpt 给出的答案是：不要把 skill 当作一次性写好的说明书，而要把它当作一个可审计、可回滚、可验证的训练对象。

开头那个问题也因此有了一个更准确的答案：Agent 的经验不一定要立刻进入模型权重，也不一定要靠一轮又一轮的整篇 prompt 重写来保存。它可以先沉淀成一份小而具体的文档，在验证集上被反复检验，再作为模型之外的“程序记忆”部署出去。

这或许才是 skill 真正有用的方向：不是让 Agent 更会说，而是让它把已经证明有效的做事方式，稳定地带到下一次任务里。
